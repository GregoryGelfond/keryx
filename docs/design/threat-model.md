# keryx — Threat model of record

**Date:** 2026-09-03 (revised through the inbound codec — its binary, text, and JSON payload forms — 2026-09-05)
**Status:** The threat model of record for keryx. It answers to the architecture (`docs/design/architecture.md`) — §5 (the surfaces), §6 (the error and totality posture), R4 (translation-only: keryx translates; a consuming service runs the solver and owns deployment) — and to the specification (`docs/specification.md`) beneath it. It commits the **security properties** the architecture's surfaces must hold. Where a property refines the architecture's prose it says so in place (see *The dependency boundary*); otherwise the architecture remains the architecture of record.

keryx ingests descriptor sets and message payloads in the binary wire format, the protobuf text format, and the protobuf JSON mapping — and, as later increments land, ASP text and overlays — supplied by callers it does not control, and hands back an ASP vocabulary and ground facts a caller reads without re-checking. It is built to a **mission-critical footing**: it may sit inside a service where the input it translates is wholly adversarial and where an availability or integrity failure is costly.

A **property** here is a *commitment* — it binds every keryx surface, present and future. What *holds* a property at a given revision is a *status*, recorded per door below. The two are kept separate: a reviewer reading keryx's code against this model must not read a commitment as a claim that the code already meets it.

## Readers

Three readers hold this document, and their fluencies differ:

- **The implementer** of a not-yet-built door (the `.lp` and answer-set doors, admission, overlays) — assumed fluent in Rust (unwinding, `catch_unwind`) and in protobuf descriptors; needs the walk sites, the generators, the per-door status.
- **The deploying operator** — assumed fluent in operating a service; needs the trust gradient, the *prefer-descriptor-sets* recommendation, the isolation requirement, and the `panic = abort` residual.
- **A reviewer reading keryx's code against this model** — needs each door's commitment and its honest status.

Where a passage serves one reader, the door sections below place it under that door rather than interleaving the three.

## The shared frame

**Adversary.** A caller who controls the entire input to a keryx door and may repeat the call. In a served deployment the concrete adversary is the **payload** sender — per request, the hot path. Out of scope: a caller who already holds a constructed `Schema` or `Mapping` (past the door — see *What is assumed trusted*), and one who controls the host process.

**Boundary vocabulary.** A *door* is a surface untrusted input crosses. The *interior* is everything reachable only from a constructed `Schema` or `Mapping`. A *walk* is any traversal over a schema or a decoded message. *Foreign code* is a dependency keryx is a client of — prost-reflect, protox, serde_json, themelios.

**The trust gradient.** The *schema* — a descriptor set, or `.proto` source — is loaded once from the operator's control plane; it is configuration, operator-trusted. The *payload* streams per request; it is adversary-controlled. keryx-core defends **both** to the bar **regardless of embedding** — it is one library and cannot know which drives it — so a deployment that accepts an untrusted schema is still defended. The gradient decides where the sharpest scrutiny falls (the payload door) and carries the *prefer-descriptor-sets* recommendation (the source door, below).

## What is defended

Each property is stated once here, generically. Its *status* per door is in *The doors*.

1. **Totality.** Every door returns a value or a typed `Diagnostic`; it never panics, aborts, or hangs. keryx's own logic is total *by construction* — no partial result beside a diagnosis, no panic reachable from foreign input (`expect`s only where an invariant discharges them), known foreign-code panic-and-abort triggers pre-empted: the descriptor pre-read refuses editions, an unrepresentable `syntax`, a package or declared name that is not a proto identifier (the leading-dot name prost-reflect panics on among them), and any `uninterpreted_option` — whose text-format value the engine would interpret with an *unbounded* recursive parser that aborts, not unwinds; and the source door refuses over-deep source and an over-large import graph before protox's unbounded recursive-descent parser or its recursive import resolution overflows the stack; and the payload door's text form refuses over-deep nesting before the engine's unbounded text-format parser sees a token, and runs that parser on a thread keryx sizes for what the guard admits; and the payload door's JSON form runs its deserializer — which bounds its own nesting, so nothing of keryx's need precede it — on a thread keryx sizes for all the deserializer admits. Where totality crosses into foreign code that can fault unforeseeably, *The dependency boundary* holds it.
   *Instrument.* Two generators, because one does not reach keryx: **arbitrary bytes** exercise the decoder's totality (they overwhelmingly fail at `DescriptorPool::decode`), and **valid encodings of structurally-invalid descriptors** — a proptest strategy over `FileDescriptorProto` (adversarial packages and names, nested types, uninterpreted options) — exercise keryx's own refusals (`MalformedDescriptor`, `MalformedOption`, the option-key path), which arbitrary bytes never reach. The second is the one that tests keryx; both are built.

2. **Bounded work — allocation and time.** No count or length read from the input sizes an allocation before it is checked against what the input carries — the "small message declaring a huge length" attack buys no memory. That is the committed allocation property, and it is what the allocation instrument holds. keryx's *own* allocation is **not** linear in the input: every schema element owns its fully-qualified name (`FqName::new(…full_name())`), Θ(*d*) long at nesting depth *d*, and the containment analysis clones full names per node and edge — so the schema is Θ(*n*·*d*). Time is likewise not linear everywhere: `recursion::mark` is quadratic in the message count by its own account. Name **qualification** is bounded, though — it advances *every* clashing sort per round, so its round count is the qualifier prefix depth, not the number of collisions an adversary can multiply (a superlinear-work class the property set had left open); the prefix depth is itself bounded by the **package-segment cap** the door imposes (a package with more dot-segments is refused, `MalformedDescriptor`) alongside the nesting cap. What bounds *d* is the depth property below; whether Θ(*n*·*d*) and the cycle analysis are *acceptable* against a deployment's limits is measurement, not commitment (recorded under *Open*).
   *Instrument.* A boundary test that a small input declaring a large length or count does not pre-allocate to it. A complexity bound would need its own instrument; none is committed, and the profile above is stated so a deployment sizes its limits to the truth, not to a false linear claim.

3. **Bounded-depth walks.** No walk over a schema or a decoded message may exhaust the stack. At each walk site where recursion depth is adversary-controlled, keryx's own walk carries an **explicit managed stack** — heap, not call stack — bounded by the input's nesting depth, itself bounded by the input length: structural, not a chosen number, so keryx's *own* translation imposes no depth ceiling and the specification's §8 (compositional nesting; no depth limit) holds for it. Foreign code decodes *before* keryx walks, though, and its decode recurses on the same nesting, so keeping that decode on a bounded-depth path is part of this property — and here the branches diverge: **(a)** rely on and verify the decoder's own recursion limit, which keeps *no ceiling of keryx's own* true and leaves §8's "no limit" a question about the engine; or **(b)** bound input depth before the engine, which *is* a keryx-imposed ceiling and so revises the §8 promise for payloads. Which branch is load-bearing — and, on (b), the §8 reconciliation it owes — is a decision the implementation pass settles, informed by the question of what prost-reflect's and protox's decode limits actually are. **Settled for the shipped doors:** the descriptor decode takes **(a)** — prost's `RECURSION_LIMIT` (100, verified; the deepest admitted lexical chain is one shallower), so *no ceiling of keryx's own* holds and §8's "no limit" is a question about the engine, not keryx. The source door takes **(b)** on *two* axes, because two recursions on that path are unbounded and abort. **(i)** keryx's source guard imposes a repo-local ceiling on **bracket depth** — `{ }` (protox-parse's message/group parser) *and* `< >` (prost-reflect's text-format parser, which re-parses an option's aggregate value unboundedly at option resolution) — deriving the ceiling from that same `RECURSION_LIMIT`. **(ii)** a **file-count budget** bounds the import graph, because protox resolves imports by recursion (`add_import` → `add_import`), an axis the per-file scan cannot see — a *chosen* number set below the measured overflow threshold, the one place this door departs from property 3's "structural, not a chosen number." The scan itself is a **bounded departure from R5** ("keryx parses no protobuf"): it reads lexical structure — brackets, strings, comments — but builds no tree and assigns no meaning, a *measure*, not a parse (named where a maintainer meets it, `source.rs`). Its **§8 discharge:** §8's "no depth limit" is about *compositional* nesting (message-typed fields, lexically flat — the payload door's, Increment 3), so a lexical cap on source does not revise the §8 promise; and keryx's *own* walk still imposes no ceiling (the managed stack). Both guards are interim — retired when protox bounds its own parser recursion (upstream, protox #105) and its import recursion. **Settled for the payload door (binary):** branch **(b)**, by a **uniform admission ceiling the walk enforces** — a payload may nest message-typed fields at most 99 levels below its root (`NESTING_CEILING = RECURSION_LIMIT − 1`, `codec::walk`), whatever its format; a deeper one is refused *totally* (`PayloadTooDeep` at the whole-payload locus, no facts beside it) by a counter on the walk's managed stack — no native recursion, so nothing to exhaust. This is a *door-admission policy*, not a limit of the translation: §8's "no depth limit" holds of keryx's path-term construction, which imposes no ceiling of its own, and §8 now says so. A format's decoder adds an *outer* bound of its own beyond the walk's: for binary, prost spends one recursion level per nested message and refuses only the 101st, so the deepest binary payload it decodes nests exactly 100 levels — the walk's ceiling is the **binding** refusal at that 100th level, and the engine's limit refuses depth 101 and beyond (`UndecodablePayload`), defense-in-depth from there. The ceiling is stated once for every format. **Settled for the payload door (textproto):** branch **(b)** again, and *ahead of* the engine: prost-reflect's text-format parser recurses natively on every nested message value and carries no depth limit of its own (no counter on its parse cycle — cited at `codec::guard`), so an over-deep text payload would overflow the stack and *abort*, which no containment frame holds, where the binary decoder's limit refuses cleanly. So a **pre-parse depth guard** (`codec::guard`) measures the text's message-value nesting first — `{ }` and `< >` openers less closers, outside string literals and `#` comments, the text format's own lexer mirrored and cited line by line — and refuses past the same uniform ceiling (`PayloadTooDeep` at the whole-payload locus, naming the depth measured and the ceiling and nothing of the text) before the parser sees a token: for textproto the guard is where the ceiling binds, and the walk's counter stands beneath it as defense-in-depth, as it stands beneath the engine's limit for binary. The guard's **dominance invariant** — the parser's live message depth never exceeds the scanner's count, for every input — holds because every parser recursion consumes exactly one `{`/`<` token the scanner also counts, and past a lexer error the scanner can only read more; with *equality* for every payload the parser accepts. Against the *walk* the count is a bound, not always the same number: the scanner counts message *values*, the walk counts message *occupants*, and the two coincide for a singular or repeated message field (one opener, one occupant) — so such a payload is admitted exactly as deep in text as on the wire — but not for a map entry, which spends two openers (the entry's and its value's) per occupant, nor for an expanded `Any`, which spends an opener on the expansion and more on whatever it nests, none of which the walk enters (`Any` is opaque to it, spec §10). So the guard **never admits deeper than the walk would** — the safe direction — and binds map-of-message and expanded-`Any` nesting *conservatively earlier*: a map-of-message chain is admitted to 49 levels in text where its wire form is admitted to 99. **Settled**, a documented consequence of bounding the parser lexically rather than by occupancy, which no bracket scan can tell apart; the ceiling's number is the same for every format, and its unit for text is the message value. The scan is the source door's scanner's sibling — the same bounded departure from R5, derived from this parser's lexer rather than protox's, the two grammars differing (`#` is the text format's one comment; `/` is a token of its `Any` syntax, never a comment marker). **The residual is closed by construction.** The parser spends between two and five call frames per nesting level by the field's form — two for an `Any` value, four for a singular message field, five for a list or map element — measured against the pinned engine at the ceiling's 99 levels as some 2.5 MB of stack in a debug build and 256 KB in release; keryx runs the parse on a thread it sizes itself (`engine::TEXTPROTO_PARSE_STACK`, 8 MiB — some three times the debug need and thirty times the release need), with the containment frame *inside* it, so no admitted payload can overflow whatever thread the caller decodes on — the margin is keryx's, not the host's, where the source door's guard leaves that residual to process isolation (*The division of labor*). **Settled for the payload door (JSON):** branch **(a)** at the engine, the walk's uniform ceiling beneath it. serde_json's deserializer bounds its own nesting — its recursion limit, on by default and never lifted, counts arrays and objects and refuses the 128th nested one (cited under *What is assumed trusted*) — and the engine's `serde` mapping recurses natively beneath that count with no counter of its own, so no guard of keryx's precedes the decode (R5's departures stay two) and the deserializer's count is the outer bound: the whole admitted payload, 127 nested containers at most, is deserialized on a thread keryx sizes for that admit (`engine::JSON_DECODE_STACK`, 8 MiB) before the walk, on the caller's thread, applies the ceiling. Which of the two binds goes by the field's form — where the wire spends one recursion level per nested message whatever the form. A chain of **singular** message fields spends one object a level and reaches the ceiling inside the count: 99 levels shred whole, symbol-equal to the same chain on the wire; 100 through 126 — every depth the deserializer admits past the ceiling — are the walk's `PayloadTooDeep`; 127 is the deserializer's own refusal, `UndecodablePayload`. So this is the one door on which the walk's counter is the binding refusal for more than a single level: here the uniform ceiling does real work, rather than standing beneath a tighter bound as defense-in-depth. A chain of **repeated** message fields spends an array and an object a level and meets the count first: 63 levels shred whole — the facts the same chain shreds to from the wire and from text — and 64, which the wire admits and shreds, is the deserializer's refusal, 35 levels short of the ceiling. A **map-of-message** chain spends the map's object and the value's object a level and so meets the count at about the same depth, 63, by the same arithmetic; and a chain through `google.protobuf.Value`, `Struct`, or `ListValue` binds earlier still, at about 50 levels, at the engine's own message-decode limit as it materialises the dynamic value — a clean decode error. Those two bindings are *documented*, from the engine's measure of record (`engine::JSON_DECODE_STACK`), and *not instrumented*: no fixture of the suite nests a recursive chain of maps of messages — its one map of messages, `maps.proto`'s `Inventory.items`, is a single level — or declares a `Value`, and the door's status says so. Every one is a refusal in the safe direction — a shallower message depth than the ceiling, never admission past it — and by a mechanism that is not the text form's: there a lexical guard over-counts openers the walk does not; here keryx scans nothing, and the deserializer counts containers the walk does not. **The residual is closed by construction**, as for text: measured against the pinned engine over the pinned deserializer, the deepest admitted singular chain needs some 896 KB of stack in a debug build and 160 KB in release, a repeated or map chain less, and the costliest form — a nest of `Any` values, each buffered by the engine and deserialized again at its depth — some 2 MB in debug and 320 KB in release; the 8 MiB thread carries the costliest four times over in debug and twenty-five in release, the containment frame inside it, so no payload the deserializer admits can overflow whatever thread the caller decodes on. **One asymmetry of reading, not of depth:** an empty payload is the empty message on the wire and as text, and no JSON value at all — `UndecodablePayload`; the JSON form's empty message is `{}`. With this the ceiling is realised for every payload format the specification names (§26): stated once, binding at three sites — the walk for binary and for a JSON chain of singular message fields, the guard for text, the deserializer's count for a JSON repeated or map chain — and the walk's managed stack beneath all of them.
   *Instrument.* A deep-nesting test that would exhaust a naive recursive walk. It attaches to the **walk** (not the door) where foreign code caps decode depth below the level the walk must survive — it cannot reach the walk through the cap — so the pass states, per door, where it attaches and what it must reach past. For the payload door it attaches at both: through the door (`tests/codec_depth.rs` — a binary payload nesting 99 shreds whole, one nesting 100 is the walk's `PayloadTooDeep`, one nesting 101 the engine's `UndecodablePayload` before any walk) and at the walk's counter, seeded past the ceiling as a deeper-admitting decoder would leave it (`codec::walk`'s tests). For the text form it attaches through the door and at the scanner: `tests/codec_textproto.rs` — 99 nested message values parse on the sized thread and shred whole, symbol-equal to the same chain on the binary wire; 100 are the guard's `PayloadTooDeep` before the parser sees a token, through either bracket pair, its detail naming no field of the payload where the parser's refusal would have; and 101, 1,000, 10,000, and 100,000 levels are refused with no call stack spent — and `codec::guard`'s tests at the scanner (comments, string literals and their escapes, concatenated literals, list brackets, unmatched closers, the newline the lexer refuses inside a literal). For the JSON form it attaches through the door at both boundaries, there being no scanner: `tests/codec_json.rs` — a chain of singular message fields 99 deep shreds whole, symbol-equal to its wire form; 100 and 126 deep, each deserialized whole on the sized thread, are the walk's `PayloadTooDeep`, naming the sort, the depth, and the ceiling and nothing of the deserializer's count; 127, 1,000, and 10,000 deep are the deserializer's `UndecodablePayload`, naming the count exceeded and nothing of the ceiling, with no walk run — the pin on the door's premise that the deserializer's limit is on, which would fail were it ever lifted; a chain of repeated message fields 63 deep shreds whole, symbol-equal to its wire and text forms, and 64, 1,000, and 10,000 deep are the deserializer's refusal, where the wire admits and shreds 64. The map-of-message and `Value` bindings have no instrument, for want of a fixture, and are stated as documented above.

4. **Integrity — no silent misrepresentation.** keryx emits facts that faithfully represent the input, or it refuses; it never emits facts that misrepresent it, and a partial result is never delivered beside a diagnosis. A scalar that does not fit its term is refused, not truncated; an interior NUL, an open-enum value, a name collision are named. A silently wrong translation is worse than a refusal here.
   *Instrument.* The refusal tests for the cases integrity turns on — at the payload door, a generator of valid encodings carrying hostile values, each checked against a model of the §6 policy: refused at its field or faithfully carried, never both and never neither (`tests/codec_totality.rs`; for the text form, a generator of text spelled in the schemas' own vocabularies drawing the same hostile values, `tests/codec_textproto.rs`; for the JSON form, the same hostile values under the mapping's own spellings — an integer as a number or as a string of digits, an enum by name or by number, the members in either order — checked against the same model, `tests/codec_json.rs`) — and the codec's round-trip property (payload → facts → payload), initiated with the inbound half at Increment 3 and completed when reassembly lands at Increment 4.

5. **Determinism.** The same input yields byte-identical vocabulary and facts. This is an **auditability** property: a translation can be reproduced and checked. Its mechanism is ordering by `Symbol::Ord` (canonical bytes), which fixes *output order* against the hidden state — a hash seed, an iteration order — that would otherwise vary it. It does not bound *time*, so it is not by itself an availability guarantee.
   *Instrument.* The golden tests in CI.

6. **Confidentiality.** Out of scope at the descriptor and payload doors: they carry no filesystem or network reach, so nothing an adversary places in them names a resource to read back. At the **source door**, whose imports name files the resolver reads and folds into the descriptor set (whence names and doc comments render, via `render_documented`, architecture §4, into the `.lp` a caller receives), it is **held**: the resolver reads only within the include roots — a traversing, absolute, or symlinked import out of them is refused (escape confinement) — and the one remaining half, a user file shadowing a reserved name *inside* a root, substitutes only in-root content, so no adversary-directed import exfiltrates file contents through the `.lp`. The recommendation below still places that door behind operator trust; two low residuals (a concurrent writer inside the root; hard links) are named at the door, outside the model's adversary.

## What is assumed trusted

- **A holder of a constructed `Schema` or `Mapping`.** It is constructible only at a door (its lists are `pub(crate)`), so possession proves it crossed one; the interior reads it without re-validating. This is the value of the typed model.
- **The dependencies, on their supported profile.** themelios, prost-reflect, protox, and — for the payload door's JSON form — serde_json are foreign code. keryx trusts them on the input it admits and does **not** trust them total on arbitrary input (prost-reflect panics on an editions set; that is pre-empted). Their misbehavior is insulated on every axis: their types never appear in keryx's surface, their structured errors are composed into keryx `Diagnostic`s, and an unforeseen *fault* on a foreign-input path is contained at *The dependency boundary*. themelios is pinned by git revision; **prost-reflect, protox, and serde_json are pinned exact (`=`)** — the pre-emption catalogue (the shapes prost-reflect panics on, its lazy option decode and unbounded aggregate parse, the protox-parse lexer the source scanner mirrors, the import budget calibrated to protox, and serde_json's recursion default, below) is a statement about their internals at exactly those versions, re-owed on any deliberate bump — as themelios pins `rowan` exact for the same coupling. (The `text-format` feature that makes the aggregate-parse abort reachable is keryx-core's own declaration now, not a transitive accident: the payload door's textproto parse calls that parser, so keryx-core declares prost-reflect's `text-format` feature itself rather than resting on `protox` enabling it — which it does today — and the `uninterpreted_option` refusal is load-bearing, not merely defensive, for as long as the text format is a payload form. keryx-core likewise declares prost-reflect's **`serde`** feature — the engine's JSON mapping, `DynamicMessage::deserialize`, which the payload door's JSON decode drives with a serde_json deserializer — and with it the engine's own `serde-value` (it buffers a well-known type's entries before it reads them; it brings `ordered-float`) and `base64` (a `bytes` field's JSON spelling) enter the build transitively, as do serde and its `serde_derive`, and `serde_core`, `itoa`, and `zmij` beneath serde_json; keryx's code names none of these, so none is a declared dependency — the lockfile pins them, and they are foreign code keryx trusts on the input it admits exactly as it trusts the engine that calls them. The feature set, `serde` now among it, is re-owed with the rest of the catalogue on any deliberate bump.) **The JSON form takes property 3's branch (a) at the engine:** it rests on serde_json's *default* recursion limit being on — its deserializer counts down from 128 and refuses the 128th nested array or object (serde_json 1.0.151 `src/de.rs:63` and `:1372-1384`), and the engine's serde mapping recurses natively beneath that count with no counter of its own — so keryx must never lift it: the `unbounded_depth` feature stays off, and `disable_recursion_limit` is not so much as compiled in. That is a claim about serde_json at exactly its pin, guarded by a boundary test at the payload door. Which bound binds *first* — the walk's uniform ceiling or serde_json's count — goes by the field's form, where the binary wire's does not (it spends one recursion level per nested message for a singular, repeated, or map field alike): a chain of singular message fields spends one object per level and reaches the walk's ceiling inside serde_json's count, so for it the walk binds and the engine's count is the outer bound, as prost's decode limit is for the binary form; a repeated or map field spends an array or object of its own per level, so for those chains serde_json's own limit binds first, at a shallower message depth than the walk's — refusal in the safe direction, never admission past the ceiling. The per-form account is settled under property 3 and recorded at the payload door. prost and prost-types stay caret, their one coupling (the decode recursion limit) guarded by a boundary test at each door it bounds — the descriptor door's lexical chain, the payload door's compositional nesting. The committed lockfile pins the rest, so under `--locked`, as CI builds it, the code keryx trusts is the code that builds.
- **The schema source, in the typical deployment** — operator configuration, not adversary input. keryx defends the schema doors regardless; the trust is the deployment's to grant, recorded not relied upon.

## The dependency boundary

Foreign code sits on more than one path, and only some carry foreign input. Containment sits at every foreign-code-meets-foreign-input crossing, and only there — by argument, not omission:

- **Descriptor-set door:** prost-reflect decodes bytes, and its accessors lazily decode as keryx's walk reads them; prost-types pre-reads for the shapes the engine cannot represent. Foreign input — *pre-empted for every shape known to panic or abort the engine* (editions, non-identifier names, an `uninterpreted_option` whose aggregate value the engine parses with an unbounded recursion) *and contained at both the decode and the walk* — the walk containment now stands as defense-in-depth behind those pre-emptions, its previously-known trigger (a deep resolved option via a lazy `options()` decode) foreclosed by the `uninterpreted_option` refusal.
- **Source door:** protox compiles source (and reads the filesystem). Foreign input — *contained here* (an unforeseen protox panic), *and pre-empted*: over-deep source (brace *and* option-aggregate nesting) and an over-large import graph are refused before protox's parser or its recursive import resolution overflows, and imports are confined to their include roots.
- **Payload door (binary, textproto, JSON):** prost-reflect decodes the payload — `DynamicMessage::decode` against the root type's descriptor for the binary wire format, `DynamicMessage::parse_text_format` for the text format, and `DynamicMessage::deserialize` driven by a serde_json deserializer for the JSON mapping — the one engine crossing per format on the payload path; the walk then reads the decoded tree through the engine's borrowing accessors, which decode nothing further, and keryx's own §6 scalar policy lowers every value. Foreign input — *contained at the decode* (`codec::engine`), in each format, recorded as **defense-in-depth with no known trigger**: no payload is known to fault the engine's binary decode, its text parse, or its JSON deserialization, whose failures are values (`UndecodablePayload`), so the frame stands behind a total door rather than in front of a known panic. The one *abort* the text parser is known for — a stack overflow on over-deep nesting, which no frame holds — is *pre-empted* ahead of it by the pre-parse guard and the sized parse thread (property 3); the JSON form's one abort axis — the same overflow beneath a deserializer that bounds its count but not the stack its count spends — is pre-empted by the sized decode thread alone, the count bounding what the thread must carry. For the text and JSON forms the frame sits inside the sized thread, on the thread the parse or deserialization runs on — the thread a panic hook consults `is_containing` from; a panic escaping it (none can, the frame catching every unwind inside it) is re-raised inside a frame on the caller's thread, so it is the same `DependencyFault` from the one seam, reported once. The JSON form's frame names **serde_json** — the code keryx calls — and the engine's `serde` visitors run beneath the deserializer inside that one frame, so a fault in either reads as that dependency's.
- **`.lp` / answer-set doors (Increments 4, 6):** themelios `parse`/`raise`. Foreign input — *contained as the doors land.*
- **Emission:** themelios `construct`/`render` runs over keryx-**constructed** values, never foreign input — interior code, trusted by the interior's own trust, needing no containment.

**The containment, and its honest ground.** At each such crossing keryx wraps the foreign call in one named `catch_unwind`, so an unforeseen unwinding fault becomes a typed `Diagnostic` rather than unwinding into the caller. Its ground is **architecture §6's totality posture — "no panics on foreign input"** — not a claim that a `Result` type forbids panics (it does not). On that ground the boundary is a **security mechanism with a named residual**, whose *motivation* is contract-honesty and the keryx user's experience; calling it "not a security guarantee" would be too modest for a reviewer deciding whether to count on it.

**The fault's diagnosis.** The contained fault surfaces as a new `DiagnosticKind`, **`DependencyFault`** (the enum is `#[non_exhaustive]`; a clean add). The case-split it serves is **asymmetric**: a *keryx* bug is a panic — keryx-core stays total by construction and mints no library "internal" kind — reported by the CLI as `Exit::Internal` ("a bug in keryx"); an *upstream* fault is `DependencyFault`, a value. It carries its own CLI exit class (a new `Exit` variant — an engine fault is neither a keryx bug nor a user's schema error). The dependency and operation keryx knows with certainty ride in the `detail` prose; the wire shape (`{field_path, kind, detail}`, specification Appendix B) is **unchanged** — the `kind` distinguishes the fault, and structured fields are not yet earned.

**The untrusted text this composes** is not unique to this boundary. Every diagnostic `detail` and `Locus` composed from input or foreign code is untrusted text — `unreadable_set` carries prost-reflect's message, `source_error` carries protox's (which quotes source), `MalformedOption` embeds a `Debug` of an adversary value, every `Locus::at(…full_name())` embeds an adversary-chosen name. So the property (composed text is escaped for the format it renders in, and length-bounded where an unbounded render would harm) belongs at the **diagnostics level**, held by the two renderers, and it differs by view: the **human view** (a terminal line) is both control-escaped and **length-bounded** — a fixed character cap on char boundaries, so an adversary's control bytes cannot steer a terminal and excess length cannot flood it; the **wire view** (machine-consumed JSON) is escaped for its format (`escape`, covering the C0 set) but bounded only by the input's own size, up to the constant escaping factor (a control byte becomes the six characters `\u00NN`) — never super-linearly — so a consumer reads the full `detail`. The one text outside a `Diagnostic` — the panic hook's opt-in `RUST_BACKTRACE` line, which prints a contained fault's payload (adversary-chosen names among it) — routes that payload through the same human bound, never raw. *Instrument (this pass):* a test that a `detail` or `Locus` carrying control bytes and excess length renders escaped and length-bounded in the human view, as `escape`'s test assures the C0 escaping for the wire.

**The panic-hook consequence, reconciled.** A panic hook runs at the panic site, *before* any `catch_unwind` unwinds. The CLI installs one (`exit::contain`) whose notice reads "this is a bug in keryx." A `DependencyFault` contained at a door would trip that hook — the user seeing "a bug in keryx" (false — the fault is upstream's, provoked by the input) *and* the `DependencyFault` diagnostic (under `--format json`, two arrays for one event). The reconciliation chosen (over swapping the global hook — process-global mutation that races other threads' panics — or neutralizing the notice — which loses the keryx-bug signal): the hook **consults `keryx_core::is_containing()`**, a thread-local set for the duration of a `fault::contain` frame, and stays silent while containing, so a contained fault reports once, as its diagnostic. Its **named residual costs**: (i) a library consumer with Rust's *default* hook still sees `panicked at …` for a contained fault, and silences it only by installing a hook that consults `is_containing`; (ii) the silence is default-only — under `RUST_BACKTRACE` the hook still emits the fault's location and backtrace, framed as a *dependency* fault (a debugging aid the operator opts into), since the returned diagnostic carries the payload message but not the location; (iii) a *non-unwinding* panic inside a frame (e.g. a `Drop` panicking during unwind) fires the hook while containing and then aborts with only the runtime's line — an accepted residual inside *The residual*'s abort case, with no stable-Rust guard (`PanicHookInfo::can_unwind` is unstable). It retired three standing statements of the old posture, updated as it landed: architecture §6, the `descriptor::decode` note, and `docs/proto-support.md`.

**The residual.** `catch_unwind` holds only an *unwinding* panic; under `panic = abort`, and for a fault that aborts, hangs, or corrupts rather than unwinds, there is nothing to catch — so the known *abort* axes are **pre-empted, not contained**: the descriptor door refuses an `uninterpreted_option` (whose aggregate the engine parses unboundedly), the source door bounds bracket depth and the import graph, the payload door's text form bounds its message nesting before that same unbounded parser and sizes the thread the parse runs on, and its JSON form sizes the thread its deserialization runs on for the deserializer's own full admit, each before the overflow. What the residual still covers — an *unforeseen* abort, `panic = abort`, a hang — is closed by *The division of labor*.

**Process-global state.** A contained fault must not poison state shared across requests. prost-reflect touches its global well-known-type pool only through `DescriptorPool::global()`, which holds the pool's lock solely across an infallible `Arc` clone (verified against the pinned source, `global.rs`), never across the panic-prone decode; its only across-fallible-work holders are the `*_global_*` mutators, which keryx never calls. So a contained fault leaves the pool usable — a clean decode in the same process still succeeds (instrumented) — and one fault cannot become a persistent denial for a long-lived service, which settles the `catch_unwind`-soundness question for the shipped doors. The payload door reads the pool only through the root descriptor's handle, in each of its three formats — the engine consults its global well-known-type pool on a descriptor's option decode and in its reflection of prost-types' own well-known types (its every `global()` site, cited at `codec::engine`), never on a payload decode, parse, or deserialization; the text parser resolves an `Any` value's type against the root descriptor's own pool, and the JSON deserialization resolves one against that same pool (`desc.parent_pool()`, cited at `codec::engine`), never the engine's global one — so no payload path touches process-global state at all. *Residual:* a same-process consumer that itself calls those global mutators with a panicking set is outside keryx's control, named here.

## The division of labor

keryx is the translation; a consuming service runs the solver and owns deployment (R4). Fault-containment divides on that line.

- **keryx guarantees:** totality (by construction, plus the contained boundary under unwinding), bounded allocation and bounded-depth walks, integrity, determinism, and the full insulation of its dependencies from its user.
- **The consuming service provides** what only a process boundary can: isolation of the translation under resource limits, so that an unforeseen fault keryx's in-process containment cannot catch — an abort, a hang, a corruption — is contained by the operating system. A mission-critical embedding runs keryx's translation isolated; keryx names the requirement and does not over-claim a total in-process guarantee. The service also owns the trust placement (a trusted schema source) and the build profile (unwinding, to keep the contained boundary live).

## The doors

Each door: its input, its trust in the typical deployment, the foreign code it invokes, its walks, its per-property **status** (*held at `b093008`* / *this pass* / *held for binary* / *held for binary and textproto* / *held for binary, textproto, and JSON* / *Increment N*), its instruments, and any operator recommendation.

### Descriptor-set door — `descriptor::ingest(&[u8])` — shipped

- **Input.** A serialized `FileDescriptorSet`. **Trust.** Schema (operator, typically). **Foreign code.** prost-reflect (`DescriptorPool::decode`, and the lazily-decoding accessors the walk reads); prost-types (the pre-read). **Walks.** `subject_messages` (gathers nested message types, a managed stack); `recursion::reaches_self` (the containment-cycle walk); the per-element `build_*` pass; the referent closure (a heap worklist that pulls in every well-known or dependency type a subject field references, §10 — each type built once, bounded by the pool's finite type set, no call-stack recursion).
- **Status.**
  - *Totality:* the structural refusals `MalformedDescriptor`/`MalformedOption` hold — *held at `b093008`*; *this pass* pre-empts every shape the engine panics or **aborts** on rather than rejects — editions, an unrecognised `syntax`, a **package or declared name that is not a proto identifier** (the leading-dot name the engine panics on among them), and any **`uninterpreted_option`** (a compiled set carries none; an unresolved one drives the engine's unbounded text-format parse of its aggregate value, an abort containment cannot hold) — and **contains an unforeseen engine fault at both the decode and the accessor walk** (the accessors lazily decode, keryx's walk holds no `unwrap`/`expect` of its own, so a walk fault is the engine's `DependencyFault`, not a keryx bug). The walk containment now stands as **defense-in-depth** behind the pre-emptions — its previously-known trigger (a deep resolved option through `options()`' lazy decode) foreclosed by the `uninterpreted_option` refusal — with a *real* contained fault demonstrated at the decode. Both totality generators are *this pass*.
  - *Bounded depth:* `recursion::reaches_self` is an explicit managed stack already — *held at `b093008`*; `subject_messages` is a managed stack *this pass* (native recursion before it).
  - *Bounded work:* the Θ(*n*·*d*) profile is the truth today; the allocation-budget instrument is *this pass*.
  - *Integrity, determinism:* *held at `b093008`* (the refusal set; the golden tests).
- **A boundary this door crosses.** The `package` string is adversary-controlled here yet reaches two sinks that each assume an identifier shape — the CLI's per-package output path (`<out>/<package>.…`, a filesystem *write*) and the emitted `#include "<package>.core.lp"` operand (a clingo directive) — so an unvalidated package could name a traversing path or inject a directive through the `.lp` a consumer loads. *This pass* refuses at the door any package that is not a dotted sequence of proto identifiers within a segment bound, and *represents* the proof: a `Package` newtype constructed only at the door and carried to `Unit::package()`, so neither sink re-derives trust from a bare string. Integrity (property 4) is thereby held for the package too — it reaches the path and the `#include` only as a validated identifier.
- **A named vector at this door.** Option admission is a **file-name heuristic** (`descriptor::options::read`: an extension is keryx's iff its declaring file is *named* `keryx/options.proto`), not true extension identity — a crafted set can self-declare that file name (`options.rs` documents this). *Totality* survives it: a non-identifier option key is diagnosed downstream (`UnmappableOptionKey`), not panicked. *Integrity* survives it **today**: no annotation semantics are consumed at the gen stage, so a spoofed registry changes only `opt/3` facts, which faithfully report what the set declared; the obligation re-arises when an annotation gains meaning (Increment 5). Replacing the file-name heuristic with true extension identity is an additive follow-up.
- **Instruments.** The two totality generators; the deep-nesting test (attaching per the depth property); the allocation-budget test; a same-process clean-decode-after-fault test (the global-pool argument).

### `.proto`-source door — `descriptor::source::compile(files, includes)` — shipped

- **Input.** `.proto` file paths and include roots. **Trust.** Schema; **not** recommended at an untrusted per-request boundary. **Foreign code.** protox (compiler and resolver chain), which **reads the filesystem**. **Walks.** the descriptor door's, downstream of the compiled set.
- **Status.** Totality, integrity, and determinism ride the descriptor door's walk over the compiled set — *held at `b093008`*. *This pass:* an unforeseen protox panic is contained (`DependencyFault`); **over-deep source and an over-large import graph are pre-empted** — keryx's guard refuses source whose **bracket depth** exceeds `SOURCE_NESTING_LIMIT` (`SourceTooDeep`), counting `{ }` message/group nesting *and* `< >` option-aggregate nesting (the aggregate value prost-reflect re-parses unboundedly at option resolution), and refuses an import graph exceeding a file-count budget (`SourceImportGraphTooLarge`), each *before* protox's unbounded parser or its recursive import resolution overflows the stack and aborts (pre-emption instances beside the descriptor pre-read, property 1). The scanner's state machine mirrors protox-parse 0.9.0's lexer, the pinned lines cited at `source.rs`. The walk over the compiled set is bounded (the managed stack) and its work bounded, as for the descriptor door; **confinement** is *held for escapes* (below). Bounded depth takes property 3's branch **(b)** on two axes (the bracket scan, structural; the import budget, a chosen number), each defense-in-depth with a **residual**: a sub-standard thread stack can abort below the bound — measured (debug) at ~900 nesting levels and ~1800 chained imports on an 8 MB main stack, and release frames are smaller (so its threshold is higher); the bounds (99 and 128) sit below the ~0.8 MB floor that scales to, closed by the consuming service's process isolation (*The division of labor*).
- **Resource selection / confinement.** This door **selects files by design**: an `import` in adversary-supplied source names a file the resolver reads and folds into the set — so its defended property is **confinement**: the resolver reads only within the include roots, not a traversing (`..`), absolute, or symlinked import out of them. **Status: held for escapes.** protox's own import-name validation rejects a `..`/absolute import *name* (`UncompilableSource`); keryx's include-root resolver canonicalises the resolved path and refuses one that escapes its root (`SourceOutsideRoot`), catching the **symlinked** escape protox does not and backstopping the rest. **WKT/registry *shadowing*** — a user file named like a well-known type or the option registry placed *inside* a root, which resolves first by chain precedence — is **not** an escape and is **not** closed by this mechanism (mechanising it would fight the deliberate "a project's own `keryx/options.proto` wins" order, `source.rs`); it is **answered** — a shadow substitutes *in-root* content for a bundled constant, so nothing outside the root is read: the confidentiality half leaves no path, and the integrity half (a shadow that redefines an option message) is the descriptor door's registry-shadowing vector, held today. **Confidentiality** (property 6): source-import exfiltration is thereby **closed**. Two low residuals sit outside the model's adversary (who supplies the root's contents at call time, not a concurrent mutator): a writer who swaps a directory component for a symlink between canonicalise and read, and a hard link inside the root to a file outside it — both need write access inside the root during the call, named not relied upon.
- **Recommendation.** At an untrusted boundary, accept a **pre-compiled descriptor set** from a trusted source; treat `.proto`-source compilation as an operator or CLI convenience. keryx-core keeps the door total and bounded regardless; the recommendation steers where the compiler-on-hostile-input surface is exposed.
- **Instruments.** The confinement tests above — *this pass* — hold the escapes (`tests/source_confinement.rs`: the symlinked escape is refused, the in-root read admitted); where a property rests on a claim about protox's behavior the repository cannot itself check, the door's status names it as such (the pinned-source citations in `source.rs`).

### Payload door — `codec::Codec::shred(root_type, payload, format, root)` — shipped for binary, textproto, and JSON

- **Input.** A message payload: the binary wire format (`PayloadFormat::Binary`; the CLI's `.binpb`), the protobuf text format (`PayloadFormat::Textproto`; the CLI's `.txtpb`), and the protobuf JSON mapping, canonical (`PayloadFormat::Json`; the CLI's `.json`) — all three as of the inbound codec, through the same `Codec`, the same walk, and the same admission policy. **Trust.** Payload — per request, the adversary's: the hot door, and the reason the model precedes the increment. **Foreign code.** prost-reflect (`DynamicMessage::decode` against the root type's descriptor for the binary format; `DynamicMessage::parse_text_format` for the text format, on a thread keryx sizes; `DynamicMessage::deserialize` for the JSON mapping, driven by a serde_json deserializer, on a thread keryx sizes; then the borrowing field accessors the walk reads, which decode nothing further) and serde_json (the JSON deserializer, whose own recursion limit is the JSON form's outer depth bound). **Walks.** the shredding walk (`codec::walk`) — an explicit heap stack of work items, one per message occupant, under the uniform nesting ceiling — over a referent index built once per codec (predicate-keyed sort and enum resolution, so the walk never searches); and, for the text format, the pre-parse depth guard's scan (`codec::guard`) ahead of the parser — one pass over the payload's bytes, allocation-free, no recursion. The JSON form adds no scan: its deserializer bounds its own nesting, and keryx reads nothing of the payload ahead of it.
- **Status.**
  - *Totality:* **held for binary, textproto, and JSON.** `Codec::shred` returns facts or typed diagnostics over any payload. Bytes that do not decode as the root type are `UndecodablePayload` — for the text form, bytes that are not UTF-8 (the text format is text) or text that does not parse as the root type, alike; for the JSON form, bytes that are not one canonical JSON value of the root type — not UTF-8, a member the type does not declare by its JSON or its proto name, a value outside its kind, a container past the deserializer's own count, text after the one value, or the empty text, which is no JSON value where the wire and the text format read the empty message from nothing (the JSON form's empty message is `{}`) — alike; each §6 refusal (`ValueOutOfRange`, `InteriorNul`, `UnrepresentableText`, `UnannotatedFloat`), an undeclared enum number (`UnknownEnumValue`), and nesting past the ceiling (`PayloadTooDeep`) is a value at its locus, collected — every fact or every diagnosis, never a partial shred beside one; the root type is resolved before any decode (`UnknownRootType`, the caller's argument error). The one engine crossing per format is contained (*The dependency boundary*), defense-in-depth with no known trigger. Both totality generators are built (`tests/codec_totality.rs`): **arbitrary bytes**, which overwhelmingly fail at the decoder while a steady share reach the walk, and **valid encodings carrying hostile values**, which exercise keryx's own refusals. The text form has its own (`tests/codec_textproto.rs`): **arbitrary text mixed with text spelled in the schemas' own vocabularies** — benign values, the values the walk refuses, parser-refused spellings, and nesting either side of the ceiling — over which the shred returns facts that render or a refusal the door's contract names, never a contained fault, and leaves no frame live on the calling thread; a fixed-seed tally pins that the generator reaches every outcome of the door — facts and each of the seven refusal kinds — so the property is exercised at every step: UTF-8, guard, parser, walk, every §6 refusal. The JSON form has its own (`tests/codec_json.rs`): **arbitrary bytes and characters mixed with JSON spelled in the schemas' own vocabularies** — benign values, the values the walk refuses, spellings the deserializer refuses, and chains nesting either side of both depth boundaries — shredded against six codecs, over which the shred returns facts that render or a refusal the door's contract names, never a contained fault, and leaves no frame live on the calling thread; its fixed-seed tally pins that the generator reaches every outcome of the door — facts and each of the seven refusal kinds, the walk's `PayloadTooDeep` among them — so the property is exercised at every step: deserializer, walk, every §6 refusal.
  - *Bounded depth:* **held for binary, textproto, and JSON** — the same uniform ceiling, 99 message-typed levels below the root, by property 3's branch (b) for binary and textproto and branch (a) at the engine for JSON, binding at a different site per format. For binary, the walk's counter: the binding refusal at a payload's 100th level; the engine's decode limit refuses the 101st and beyond, defense-in-depth from there. For textproto, the pre-parse guard: the binding refusal at a payload's 100th message *value* *before* the engine's unbounded text parser sees a token — the 100th occupant level for singular and repeated message fields, a shallower one for map-of-message and expanded `Any`, which spend openers the walk does not count (conservative, never permissive; property 3) — the walk's counter beneath it; and the parse itself on a thread keryx sizes for the deepest admitted payload (8 MiB against a measured 2.5 MB debug need), so the residual a sub-standard caller thread would be is closed by construction. For JSON, no guard, and the deserializer's own count as the outer bound (127 nested containers admitted, the 128th refused): the walk's counter is the binding refusal for a chain of singular message fields — at the 100th level and every level to the 126th, the deserializer's deepest admit, each deserialized whole on the sized thread before the walk refuses it — with the count refusing the 127th; for a repeated or map-of-message chain the count binds first, at about 63 levels (two containers a level), and for a `google.protobuf.Value` chain the engine's own message-decode limit at about 50 — shallower than the ceiling, never past it (conservative, never permissive; property 3); and the whole admitted payload deserialized on a thread keryx sizes for the deserializer's full admit (8 MiB against a measured 2 MB debug need for the costliest form, a nest of `Any` values), so the same residual is closed by construction. Instrument: `tests/codec_depth.rs` through the door and `codec::walk`'s seeded-counter tests at the walk, for binary; `tests/codec_textproto.rs` through the door (99 levels shred whole on the sized thread, 100 are refused before the parse through either bracket pair, far past it with no call stack spent, and the guard is shown to run before the parser and to measure exactly what it would) and `codec::guard`'s tests at the scanner, for textproto; `tests/codec_json.rs` through the door at both boundaries, for JSON (a singular chain at 99, 100, 126, and 127; a repeated chain at 63 and 64; 1,000 and 10,000 in either form, with no walk run) — the map-of-message and `Value` bindings stated from the engine's measure of record, not instrumented, for want of a fixture that nests them.
  - *Bounded work:* **held for binary** on allocation — the wire declares lengths, never counts, and a few bytes whose varint length claims ~1 GiB yield `UndecodablePayload` without a reservation of the declared size (`tests/codec_allocation_budget.rs`, a counting allocator) — and **held for textproto by the format's shape**: the text format declares no length or count at all, so nothing read from the input can size an allocation ahead of what the input carries; the guard's scan allocates nothing, and the parse thread's stack is reserved address space committed a page at a time as the parse descends, so a shallow payload pays one thread spawn and little else — the one cost the binary form does not pay, stated at `PayloadFormat::Textproto`; and **held for JSON by the format's shape** on the same argument: the JSON mapping declares no length or count either, so nothing read from the input can size an allocation ahead of what the input carries (the engine's buffering of an `Any` whose `@type` follows its value holds what the input carried, no more), and the decode thread's stack is likewise reserved address space committed as the deserialization descends — the same one thread spawn per payload, stated at `PayloadFormat::Json`. The shred's profile, stated so a deployment sizes to the truth: the decoded tree is held once and borrowed through the accessors (`Cow::Borrowed`, cited at `codec::engine`), never cloned per level; the facts are linear in the payload's size *times* its nesting depth, since every fact carries its full path term (spec §4.1), with the depth bounded by the ceiling; and `Facts` holds the facts once, as symbols — the facts' memory steady-state, and up to three times it transiently while the `.lp` text renders (the program derived from the symbols, then the text, beside them).
  - *Integrity:* **held for binary, textproto, and JSON** — a value is refused or faithfully carried, never both and never neither (the hostile-value generator checks each against a model of the §6 policy; the text generator draws the same refused values, and its fixed-seed tally pins that each refusal is reached; the JSON form's two generators do the same — its vocabulary generator draws the refused values as the mapping spells them, and its fixed-seed tally pins that each refusal is reached, while its hostile-value generator over the refusals probe, under the spellings the mapping admits for one value — an integer as a number or as a string of digits, an enum by name or by number, the members in either order — is checked against the same model); an open-enum number is named, never mapped to a constant it is not; no partial shred is delivered. The committed example's three forms shred to one golden; the text format's alternative spellings of one message — the `[ ]` list form, `< >` for `{ }`, reordered fields, comments, concatenated literals — are one shred, and so are the JSON mapping's — a field by its JSON name or its proto name, an integer as a number or a string of digits, a character raw or escaped, the members in any order, whitespace anywhere (spec §26: spelling is not content). What a payload is *admitted* to is where the three forms part, each an over-refusal and never a misrepresentation: map-of-message and expanded-`Any` nesting binds earlier in text, repeated-message and map-of-message nesting earlier in JSON (property 3); and the empty text, no JSON value, is refused where the other two forms read the empty message — a refusal, never a misreading. The round-trip half of the instrument completes with reassembly (Increment 4).
  - *Determinism:* **held for binary, textproto, and JSON** — the same payload yields byte-identical facts on both seams (`Symbol::Ord` on the symbol seam, themelios's statement order on the `.lp` seam), whatever the wire's field order and whatever order the engine's map table hands entries back in (keryx sorts a map's entries by key, once), and every fact is delivered exactly once on each seam even from a wire that repeats a field (`tests/codec_determinism.rs`); a text payload's facts are the same function of the payload a binary one's are — the parse thread exists for its stack alone, the caller waits on it, and the tree comes back owned, so the parse is single-threaded for all that it runs on its own thread, and a JSON payload's likewise, its decode thread existing for its stack alone; a JSON object that repeats a member reads as a wire that repeats a field does — the last occurrence wins, one fact — and a map's entries shred key-sorted whatever order the object spells them in (`tests/codec_json.rs`); the thermal example's facts are golden in all three committed forms (`tests/thermal_example.rs`, `tests/codec_textproto.rs`, `tests/codec_json.rs`).
- **The untrusted text this door composes.** A refusal's `detail` names a string value's offending *position* — a NUL's offset, a control character's code point and offset — never the string itself (a payload's text being the adversary's to flood a diagnostic with); an out-of-range or undeclared number is named as a number; a `Locus` is the field's fully-qualified proto path, schema text admitted at the descriptor door; and `UndecodablePayload` composes the engine's own message — or, for the JSON form, the deserializer's, which names a member or an enum value the type does not declare in the payload's own spelling (`unrecognized field name '…'`), adversary text verbatim — held to the diagnostics-level rendering bound like every other, and to no weaker one; the one `detail` that echoes caller text verbatim, `UnknownRootType`'s (`codec::walk`'s `unknown_root_type` names the `root_type` argument as given), quotes the caller's own argument — outside this door's payload-sender adversary, and bounded at the diagnostics level regardless.
- **Instruments.** `tests/codec_totality.rs` (both generators), `tests/codec_depth.rs`, `tests/codec_allocation_budget.rs`, `tests/codec_determinism.rs`, `tests/codec_wkt.rs` (a referenced well-known type is an ordinary sort on the way in, spec §10), `tests/codec_thermal.rs` and `tests/thermal_example.rs` (the story's facts, golden). For the text form, `tests/codec_textproto.rs` (parity of the committed example's two forms and of the format's alternative spellings; the door's own refusals — not UTF-8, not parsing as the root type — at the whole-payload locus; the ceiling through the door, before the parse, and the ordering witness that the guard runs first; totality over arbitrary and vocabulary-spelled text, with the fixed-seed reach tally) and `codec::guard`'s scanner tests. For the JSON form, `tests/codec_json.rs` (three-way parity of the committed example's forms and of the mapping's alternative spellings; the door's own refusals — not UTF-8, not one canonical value of the root type, the empty text — at the whole-payload locus; both depth boundaries through the door, with the pin that the deserializer's limit is on; totality over arbitrary and vocabulary-spelled JSON, with the fixed-seed reach tally; the hostile-value generator against the §6 model under the mapping's spellings; determinism on both seams), and the CLI's `facts` test over a `.json` payload of the §28 batch, shredding to the same facts as its `.binpb`.
