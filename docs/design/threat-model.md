# keryx — Threat model of record

**Date:** 2026-09-03 (revised through the inbound codec — its binary, text, and JSON payload forms — 2026-09-05; extended to the outbound door — the reassembler in all three forms, the `.lp` read, and `keryx emit` — 2026-09-06)
**Status:** The threat model of record for keryx. It answers to the architecture (`docs/design/architecture.md`) — §5 (the surfaces), §6 (the error and totality posture), R4 (translation-only: keryx translates; a consuming service runs the solver and owns deployment) — and to the specification (`docs/specification.md`) beneath it. It commits the **security properties** the architecture's surfaces must hold. Where a property refines the architecture's prose it says so in place (see *The dependency boundary*); otherwise the architecture remains the architecture of record.

keryx ingests descriptor sets and message payloads in the binary wire format, the protobuf text format, and the protobuf JSON mapping — and, as the outbound and later increments land, answer sets (as symbols, or as `.lp` text), `.lp` modules, and overlays — supplied by callers it does not control, and hands back an ASP vocabulary, ground facts, and reassembled messages a caller reads without re-checking. It is built to a **mission-critical footing**: it may sit inside a service where the input it translates is wholly adversarial and where an availability or integrity failure is costly.

A **property** here is a *commitment* — it binds every keryx surface, present and future. What *holds* a property at a given revision is a *status*, recorded per door below. The two are kept separate: a reviewer reading keryx's code against this model must not read a commitment as a claim that the code already meets it.

## Readers

Three readers hold this document, and their fluencies differ:

- **The implementer** of a not-yet-built door (the outbound door — the answer set's, and the CLI's `.lp` read — admission, overlays) — assumed fluent in Rust (unwinding, `catch_unwind`) and in protobuf descriptors; needs the walk sites, the generators, the per-door status.
- **The deploying operator** — assumed fluent in operating a service; needs the trust gradient, the *prefer-descriptor-sets* recommendation, the isolation requirement, and the `panic = abort` residual.
- **A reviewer reading keryx's code against this model** — needs each door's commitment and its honest status.

Where a passage serves one reader, the door sections below place it under that door rather than interleaving the three.

## The shared frame

**Adversary.** A caller who controls the entire input to a keryx door and may repeat the call. In a served deployment the concrete adversary is the **payload** sender — per request, the hot path. Out of scope: a caller who already holds a constructed `Schema` or `Mapping` (past the door — see *What is assumed trusted*), and one who controls the host process.

**Boundary vocabulary.** A *door* is a surface untrusted input crosses. The *interior* is everything reachable only from a constructed `Schema` or `Mapping`. A *walk* is any traversal over a schema or a decoded message. *Foreign code* is a dependency keryx is a client of — prost-reflect, protox, serde_json, themelios.

**The trust gradient.** The *schema* — a descriptor set, or `.proto` source — is loaded once from the operator's control plane; it is configuration, operator-trusted. The *payload* streams per request; it is adversary-controlled. keryx-core defends **both** to the bar **regardless of embedding** — it is one library and cannot know which drives it — so a deployment that accepts an untrusted schema is still defended. The gradient decides where the sharpest scrutiny falls (the payload door) and carries the *prefer-descriptor-sets* recommendation (the source door, below). The *answer set* the outbound door reads — the consuming tool's solver's output over facts the payload sender shaped, or a `.lp` fixture — sits at the payload's end of the gradient: it is defended as the payload is, adversary-controlled, per request (the outbound door, below).

## What is defended

Each property is stated once here, generically. Its *status* per door is in *The doors*.

1. **Totality.** Every door returns a value or a typed `Diagnostic`; it never panics, aborts, or hangs. keryx's own logic is total *by construction* — no partial result beside a diagnosis, no panic reachable from foreign input (`expect`s only where an invariant discharges them), known foreign-code panic-and-abort triggers pre-empted: the descriptor pre-read refuses editions, an unrepresentable `syntax`, a package or declared name that is not a proto identifier (the leading-dot name prost-reflect panics on among them), and any `uninterpreted_option` — whose text-format value the engine would interpret with an *unbounded* recursive parser that aborts, not unwinds; and the source door refuses over-deep source and an over-large import graph before protox's unbounded recursive-descent parser or its recursive import resolution overflows the stack; and the payload door's text form refuses over-deep nesting before the engine's unbounded text-format parser sees a token, and runs that parser on a thread keryx sizes for what the guard admits; and the payload door's JSON form runs its deserializer — which bounds its own nesting, so nothing of keryx's need precede it — on a thread keryx sizes for all the deserializer admits; and — at the outbound door — the reassembler sets every field of the message it builds only through the engine's *validating* setter, after keryx's own inverse §6 lowering, so the engine's mismatch panics at encode are foreclosed before any message exists to encode, refuses reconstruction past the uniform ceiling before the engine's serializers, which bound nothing of their own, recurse, and runs the encode on a thread keryx sizes — while the `.lp` read needs no pre-emption of keryx's, themelios's parser bounding its own nesting and its raise being total. Where totality crosses into foreign code that can fault unforeseeably, *The dependency boundary* holds it.
   *Instrument.* Two generators, because one does not reach keryx: **arbitrary bytes** exercise the decoder's totality (they overwhelmingly fail at `DescriptorPool::decode`), and **valid encodings of structurally-invalid descriptors** — a proptest strategy over `FileDescriptorProto` (adversarial packages and names, nested types, uninterpreted options) — exercise keryx's own refusals (`MalformedDescriptor`, `MalformedOption`, the option-key path), which arbitrary bytes never reach. The second is the one that tests keryx; both are built. The outbound door owes the same pair — arbitrary symbols, which mostly bounce at its index, and symbols spelled in the schema's own vocabulary carrying hostile values, with a fixed-seed tally that the generator reaches every outcome of the door — committed, *Increment 4* (the door).

2. **Bounded work — allocation and time.** No count or length read from the input sizes an allocation before it is checked against what the input carries — the "small message declaring a huge length" attack buys no memory. That is the committed allocation property, and it is what the allocation instrument holds. keryx's *own* allocation is **not** linear in the input: every schema element owns its fully-qualified name (`FqName::new(…full_name())`), Θ(*d*) long at nesting depth *d*, and the containment analysis clones full names per node and edge — so the schema is Θ(*n*·*d*). Time is likewise not linear everywhere: `recursion::mark` is quadratic in the message count by its own account. Name **qualification** is bounded, though — it advances *every* clashing sort per round, so its round count is the qualifier prefix depth, not the number of collisions an adversary can multiply (a superlinear-work class the property set had left open); the prefix depth is itself bounded by the **package-segment cap** the door imposes (a package with more dot-segments is refused, `MalformedDescriptor`) alongside the nesting cap. What bounds *d* is the depth property below; whether Θ(*n*·*d*) and the cycle analysis are *acceptable* against a deployment's limits is measurement, not commitment (recorded under *Open*). The outbound door's own profile — an index over the answer set, a walk over the index, one sized encode thread per root — is stated at the door, committed ahead of its code.
   *Instrument.* A boundary test that a small input declaring a large length or count does not pre-allocate to it. A complexity bound would need its own instrument; none is committed, and the profile above is stated so a deployment sizes its limits to the truth, not to a false linear claim.

3. **Bounded-depth walks.** No walk over a schema or a decoded message may exhaust the stack. At each walk site where recursion depth is adversary-controlled, keryx's own walk carries an **explicit managed stack** — heap, not call stack — bounded by the input's nesting depth, itself bounded by the input length: structural, not a chosen number, so keryx's *own* translation imposes no depth ceiling and the specification's §8 (compositional nesting; no depth limit) holds for it. Foreign code decodes *before* keryx walks, though, and its decode recurses on the same nesting, so keeping that decode on a bounded-depth path is part of this property — and here the branches diverge: **(a)** rely on and verify the decoder's own recursion limit, which keeps *no ceiling of keryx's own* true and leaves §8's "no limit" a question about the engine; or **(b)** bound input depth before the engine, which *is* a keryx-imposed ceiling and so revises the §8 promise for payloads. Which branch is load-bearing — and, on (b), the §8 reconciliation it owes — is a decision the implementation pass settles, informed by the question of what prost-reflect's and protox's decode limits actually are. **Settled for the shipped doors:** the descriptor decode takes **(a)** — prost's `RECURSION_LIMIT` (100, verified; the deepest admitted lexical chain is one shallower), so *no ceiling of keryx's own* holds and §8's "no limit" is a question about the engine, not keryx. The source door takes **(b)** on *two* axes, because two recursions on that path are unbounded and abort. **(i)** keryx's source guard imposes a repo-local ceiling on **bracket depth** — `{ }` (protox-parse's message/group parser) *and* `< >` (prost-reflect's text-format parser, which re-parses an option's aggregate value unboundedly at option resolution) — deriving the ceiling from that same `RECURSION_LIMIT`. **(ii)** a **file-count budget** bounds the import graph, because protox resolves imports by recursion (`add_import` → `add_import`), an axis the per-file scan cannot see — a *chosen* number set below the measured overflow threshold, the one place this door departs from property 3's "structural, not a chosen number." The scan itself is a **bounded departure from R5** ("keryx parses no protobuf"): it reads lexical structure — brackets, strings, comments — but builds no tree and assigns no meaning, a *measure*, not a parse (named where a maintainer meets it, `source.rs`). Its **§8 discharge:** §8's "no depth limit" is about *compositional* nesting (message-typed fields, lexically flat — the payload door's, Increment 3), so a lexical cap on source does not revise the §8 promise; and keryx's *own* walk still imposes no ceiling (the managed stack). Both guards are interim — retired when protox bounds its own parser recursion (upstream, protox #105) and its import recursion. **Settled for the payload door (binary):** branch **(b)**, by a **uniform admission ceiling the walk enforces** — a payload may nest message-typed fields at most 99 levels below its root (`NESTING_CEILING = RECURSION_LIMIT − 1`, `codec::walk`), whatever its format; a deeper one is refused *totally* (`PayloadTooDeep` at the whole-payload locus, no facts beside it) by a counter on the walk's managed stack — no native recursion, so nothing to exhaust. This is a *door-admission policy*, not a limit of the translation: §8's "no depth limit" holds of keryx's path-term construction, which imposes no ceiling of its own, and §8 now says so. A format's decoder adds an *outer* bound of its own beyond the walk's: for binary, prost spends one recursion level per nested message and refuses only the 101st, so the deepest binary payload it decodes nests exactly 100 levels — the walk's ceiling is the **binding** refusal at that 100th level, and the engine's limit refuses depth 101 and beyond (`UndecodablePayload`), defense-in-depth from there. The ceiling is stated once for every format. **Settled for the payload door (textproto):** branch **(b)** again, and *ahead of* the engine: prost-reflect's text-format parser recurses natively on every nested message value and carries no depth limit of its own (no counter on its parse cycle — cited at `codec::guard`), so an over-deep text payload would overflow the stack and *abort*, which no containment frame holds, where the binary decoder's limit refuses cleanly. So a **pre-parse depth guard** (`codec::guard`) measures the text's message-value nesting first — `{ }` and `< >` openers less closers, outside string literals and `#` comments, the text format's own lexer mirrored and cited line by line — and refuses past the same uniform ceiling (`PayloadTooDeep` at the whole-payload locus, naming the depth measured and the ceiling and nothing of the text) before the parser sees a token: for textproto the guard is where the ceiling binds, and the walk's counter stands beneath it as defense-in-depth, as it stands beneath the engine's limit for binary. The guard's **dominance invariant** — the parser's live message depth never exceeds the scanner's count, for every input — holds because every parser recursion consumes exactly one `{`/`<` token the scanner also counts, and past a lexer error the scanner can only read more; with *equality* for every payload the parser accepts. Against the *walk* the count is a bound, not always the same number: the scanner counts message *values*, the walk counts message *occupants*, and the two coincide for a singular or repeated message field (one opener, one occupant) — so such a payload is admitted exactly as deep in text as on the wire — but not for a map entry, which spends two openers (the entry's and its value's) per occupant, nor for an expanded `Any`, which spends an opener on the expansion and more on whatever it nests, none of which the walk enters (`Any` is opaque to it, spec §10). So the guard **never admits deeper than the walk would** — the safe direction — and binds map-of-message and expanded-`Any` nesting *conservatively earlier*: a map-of-message chain is admitted to 49 levels in text where its wire form is admitted to 99. **Settled**, a documented consequence of bounding the parser lexically rather than by occupancy, which no bracket scan can tell apart; the ceiling's number is the same for every format, and its unit for text is the message value. The scan is the source door's scanner's sibling — the same bounded departure from R5, derived from this parser's lexer rather than protox's, the two grammars differing (`#` is the text format's one comment; `/` is a token of its `Any` syntax, never a comment marker). **The residual is closed by construction.** The parser spends between two and five call frames per nesting level by the field's form — two for an `Any` value, four for a singular message field, five for a list or map element — measured against the pinned engine at the ceiling's 99 levels as some 2.5 MB of stack in a debug build and 256 KB in release; keryx runs the parse on a thread it sizes itself (`engine::TEXTPROTO_PARSE_STACK`, 8 MiB — some three times the debug need and thirty times the release need), with the containment frame *inside* it, so no admitted payload can overflow whatever thread the caller decodes on — the margin is keryx's, not the host's, where the source door's guard leaves that residual to process isolation (*The division of labor*). **Settled for the payload door (JSON):** branch **(a)** at the engine, the walk's uniform ceiling beneath it. serde_json's deserializer bounds its own nesting — its recursion limit, on by default and never lifted, counts arrays and objects and refuses the 128th nested one (cited under *What is assumed trusted*) — and the engine's `serde` mapping recurses natively beneath that count with no counter of its own, so no guard of keryx's precedes the decode (R5's departures stay two) and the deserializer's count is the outer bound: the whole admitted payload, 127 nested containers at most, is deserialized on a thread keryx sizes for that admit (`engine::JSON_DECODE_STACK`, 8 MiB) before the walk, on the caller's thread, applies the ceiling. Which of the two binds goes by the field's form — where the wire spends one recursion level per nested message whatever the form. A chain of **singular** message fields spends one object a level and reaches the ceiling inside the count: 99 levels shred whole, symbol-equal to the same chain on the wire; 100 through 126 — every depth the deserializer admits past the ceiling — are the walk's `PayloadTooDeep`; 127 is the deserializer's own refusal, `UndecodablePayload`. So this is the one door on which the walk's counter is the binding refusal for more than a single level: here the uniform ceiling does real work, rather than standing beneath a tighter bound as defense-in-depth. A chain of **repeated** message fields spends an array and an object a level and meets the count first: 63 levels shred whole — the facts the same chain shreds to from the wire and from text — and 64, which the wire admits and shreds, is the deserializer's refusal, 35 levels short of the ceiling. A **map-of-message** chain spends the map's object and the value's object a level and so meets the count at about the same depth, 63, by the same arithmetic; and a chain through `google.protobuf.Value`, `Struct`, or `ListValue` binds earlier still, at about 50 levels, at the engine's own message-decode limit as it materialises the dynamic value — a clean decode error. Those two bindings are *documented*, from the engine's measure of record (`engine::JSON_DECODE_STACK`), and *not instrumented*: no fixture of the suite nests a recursive chain of maps of messages — its one map of messages, `maps.proto`'s `Inventory.items`, is a single level — or declares a `Value`, and the door's status says so. Every one is a refusal in the safe direction — a shallower message depth than the ceiling, never admission past it — and by a mechanism that is not the text form's: there a lexical guard over-counts openers the walk does not; here keryx scans nothing, and the deserializer counts containers the walk does not. **The residual is closed by construction**, as for text: measured against the pinned engine over the pinned deserializer, the deepest admitted singular chain needs some 896 KB of stack in a debug build and 160 KB in release, a repeated or map chain less, and the costliest form — a nest of `Any` values, each buffered by the engine and deserialized again at its depth — some 2 MB in debug and 320 KB in release; the 8 MiB thread carries the costliest four times over in debug and twenty-five in release, the containment frame inside it, so no payload the deserializer admits can overflow whatever thread the caller decodes on. **One asymmetry of reading, not of depth:** an empty payload is the empty message on the wire and as text, and no JSON value at all — `UndecodablePayload`; the JSON form's empty message is `{}`. With this the ceiling is realised for every payload format the specification names (§26): stated once, binding at three sites — the walk for binary and for a JSON chain of singular message fields, the guard for text, the deserializer's count for a JSON repeated or map chain — and the walk's managed stack beneath all of them. **Committed for the outbound door (Increment 4), ahead of its code — two crossings, one branch each.** The **`.lp` read** takes branch **(a)** at themelios, as the JSON form takes it at the engine: `parse` bounds its own nesting (`NestingLimit::DEFAULT`; past it a `nesting-too-deep` diagnostic — a value, not an overflow; total, iterative, and proven not to overflow on a 2 MiB stack), and `raise` is total (never a panic; O(tree); its diagnostics values) with its program-tier walks iterative, proven stack-safe 200,000 deep on a 256 KiB stack — so **no pre-parse guard of keryx's** precedes them (R5's departures stay two), and the crossing's containment stands as defense-in-depth with no known trigger. These are claims about themelios at exactly its pinned revision, re-owed on bump (*What is assumed trusted*). The **encode** takes branch **(b)**, by the *same* uniform ceiling: every prost-reflect serializer recurses natively on message nesting with no self-limit — `encode_raw` → `encode_field` → the nested `encode_raw` (prost-reflect 0.16.5 `src/dynamic/message.rs:134`), `fmt_message` → `fmt_field_value` → `fmt_message` (`src/dynamic/text_format/format.rs:106`, `:112`), and its `serde` serializer likewise — so the reassembly walk, an explicit heap stack top-down from each root, refuses an occupant chain past `walk::NESTING_CEILING` (`ReassembledTooDeep`, no message beside it) *before* any message is built or encoded. That is the inbound constant itself, not a second 99 — the two ceilings coupled by construction — and its §8 discharge is the payload door's: a door-admission policy, keryx's own path-term reading imposing no ceiling of its own. Depth-bounding alone does not close the abort axis, though: a message admitted *at* the ceiling is still 99 levels deep, and the encode then recurses 99 levels natively on whatever thread the caller reassembles on — a stack overflow aborts, which no containment frame holds. So the encode runs on a thread keryx sizes (`engine::ENCODE_STACK`, 8 MiB) with the containment frame *inside* it, exactly as the text parse and the JSON decode run — the margin keryx's, not the host's — and the residual a sub-standard caller thread would be is closed by construction here too. The 8 MiB is sized by the inbound threads' precedent, and now **measured** against the pinned engine in debug and release at the ceiling's 99 levels: the costliest of the three encoders needs some 640 KiB in a debug build (576 KiB overflows) and 192 KiB in release — the encode cheaper than the inbound text parse — so the 8 MiB carries it some twelve times over in debug and forty in release, the measure cited at the constant as `TEXTPROTO_PARSE_STACK` and `JSON_DECODE_STACK` cite theirs.
   *Instrument.* A deep-nesting test that would exhaust a naive recursive walk. It attaches to the **walk** (not the door) where foreign code caps decode depth below the level the walk must survive — it cannot reach the walk through the cap — so the pass states, per door, where it attaches and what it must reach past. For the payload door it attaches at both: through the door (`tests/codec_depth.rs` — a binary payload nesting 99 shreds whole, one nesting 100 is the walk's `PayloadTooDeep`, one nesting 101 the engine's `UndecodablePayload` before any walk) and at the walk's counter, seeded past the ceiling as a deeper-admitting decoder would leave it (`codec::walk`'s tests). For the text form it attaches through the door and at the scanner: `tests/codec_textproto.rs` — 99 nested message values parse on the sized thread and shred whole, symbol-equal to the same chain on the binary wire; 100 are the guard's `PayloadTooDeep` before the parser sees a token, through either bracket pair, its detail naming no field of the payload where the parser's refusal would have; and 101, 1,000, 10,000, and 100,000 levels are refused with no call stack spent — and `codec::guard`'s tests at the scanner (comments, string literals and their escapes, concatenated literals, list brackets, unmatched closers, the newline the lexer refuses inside a literal). For the JSON form it attaches through the door at both boundaries, there being no scanner: `tests/codec_json.rs` — a chain of singular message fields 99 deep shreds whole, symbol-equal to its wire form; 100 and 126 deep, each deserialized whole on the sized thread, are the walk's `PayloadTooDeep`, naming the sort, the depth, and the ceiling and nothing of the deserializer's count; 127, 1,000, and 10,000 deep are the deserializer's `UndecodablePayload`, naming the count exceeded and nothing of the ceiling, with no walk run — the pin on the door's premise that the deserializer's limit is on, which would fail were it ever lifted; a chain of repeated message fields 63 deep shreds whole, symbol-equal to its wire and text forms, and 64, 1,000, and 10,000 deep are the deserializer's refusal, where the wire admits and shreds 64. The map-of-message and `Value` bindings have no instrument, for want of a fixture, and are stated as documented above. For the outbound door (committed, *Increment 4*) it attaches at the reassembly walk — an occupant chain nesting past the ceiling is `ReassembledTooDeep` before any encode, no native recursion spent — and at the encode: a ceiling-deep reassembled message encodes to bytes on the sized thread when run from a sub-standard caller thread, so the caller's stack is shown not to carry it; and, for the `.lp` read, through the door — arbitrary text raises to symbols or is `UnreadableAnswerSet`, never a panic — the branch-(a) instrument.

4. **Integrity — no silent misrepresentation.** keryx emits facts that faithfully represent the input, or it refuses; it never emits facts that misrepresent it, and a partial result is never delivered beside a diagnosis. A scalar that does not fit its term is refused, not truncated; an interior NUL, an open-enum value, a name collision are named. A silently wrong translation is worse than a refusal here. Outbound the same property, inverted: the door emits a message that faithfully represents the answer set, or it refuses — a term that does not lower to its field's declared type, a duplicate singular, a sequence index not dense from zero, an undeclared enum constant, a number outside its kind's range, a field atom over a slot whose occupancy atom is absent, are each named at their field path (field paths, not atoms), never dropped, coerced, or serialized as the nearest value; and a message is emitted only when no diagnosis stands beside it.
   *Instrument.* The refusal tests for the cases integrity turns on — at the payload door, a generator of valid encodings carrying hostile values, each checked against a model of the §6 policy: refused at its field or faithfully carried, never both and never neither (`tests/codec_totality.rs`; for the text form, a generator of text spelled in the schemas' own vocabularies drawing the same hostile values, `tests/codec_textproto.rs`; for the JSON form, the same hostile values under the mapping's own spellings — an integer as a number or as a string of digits, an enum by name or by number, the members in either order — checked against the same model, `tests/codec_json.rs`) — and the codec's round-trip property (payload → facts → payload on canonical forms, and facts → payload → facts), initiated with the inbound half at Increment 3 and completed when reassembly lands at Increment 4 — where the outbound door's own refusal generator, over hostile values spelled in the vocabulary, joins it (the door).

5. **Determinism.** The same input yields byte-identical vocabulary and facts. This is an **auditability** property: a translation can be reproduced and checked. Its mechanism is ordering by `Symbol::Ord` (canonical bytes), which fixes *output order* against the hidden state — a hash seed, an iteration order — that would otherwise vary it. It does not bound *time*, so it is not by itself an availability guarantee. Outbound it is the specification's *identical answer set ⇒ identical bytes* (§26): sequences ordered by index, maps by key, roots by their marker atom's `Symbol::Ord` — and a set's members by `Symbol::Ord` when sets arrive with their annotation (Increment 5).
   *Instrument.* The golden tests in CI.

6. **Confidentiality.** Out of scope at the descriptor and payload doors, and at the outbound door: they carry no filesystem or network reach, so nothing an adversary places in them names a resource to read back — the outbound door reads its `.lp` text as facts and nothing else (a directive in it, an `#include` among them, is a non-fact statement, refused, never resolved: themelios parses and renders the directive and reads no file for it). At the **source door**, whose imports name files the resolver reads and folds into the descriptor set (whence names and doc comments render, via `render_documented`, architecture §4, into the `.lp` a caller receives), it is **held**: the resolver reads only within the include roots — a traversing, absolute, or symlinked import out of them is refused (escape confinement) — and the one remaining half, a user file shadowing a reserved name *inside* a root, substitutes only in-root content, so no adversary-directed import exfiltrates file contents through the `.lp`. The recommendation below still places that door behind operator trust; two low residuals (a concurrent writer inside the root; hard links) are named at the door, outside the model's adversary.

## What is assumed trusted

- **A holder of a constructed `Schema` or `Mapping`.** It is constructible only at a door (its lists are `pub(crate)`), so possession proves it crossed one; the interior reads it without re-validating. This is the value of the typed model.
- **The dependencies, on their supported profile.** themelios, prost-reflect, protox, and — for the payload door's JSON form — serde_json are foreign code. keryx trusts them on the input it admits and does **not** trust them total on arbitrary input (prost-reflect panics on an editions set; that is pre-empted). Their misbehavior is insulated on every axis: their types never appear in keryx's surface, their structured errors are composed into keryx `Diagnostic`s, and an unforeseen *fault* on a foreign-input path is contained at *The dependency boundary*. themelios is pinned by git revision; **prost-reflect, protox, and serde_json are pinned exact (`=`)** — the pre-emption catalogue (the shapes prost-reflect panics on, its lazy option decode and unbounded aggregate parse, the strict default its JSON mapping deserializes under, and — for the outbound door — the `(Value, Kind)` pairing its validating setter and its encoders agree on and the self-limit its serializers lack, and the textproto **output** grammar `codec::canonical_text` re-parses to re-order map entries (with `expand_any` off, so a `google.protobuf.Any` stays raw rather than expanding to a shape the canonicaliser cannot parse); the protox-parse lexer the source scanner mirrors and the import budget calibrated to protox; and serde_json's recursion default — the two JSON defaults below, and the outbound pairing after them; and serde_json's `preserve_order` feature staying off, so its `Value` object is a sorted `BTreeMap` and the outbound JSON encode's map order is deterministic) is a statement about their internals at exactly those versions, re-owed on any deliberate bump — as themelios pins `rowan` exact for the same coupling. The outbound door's `.lp` read — the single `themelios_program::raise_source` door, so the codec's `answer` reader names only the program tier (the syntax tier is transitive) — rests on themelios's internals at exactly its pinned revision in the same way — its parser's nesting limit, the totality of its raise (property 3, branch (a)), and that `raise_source` resolves no `#include` or other directive by reading the filesystem (the basis for the confidentiality property's out-of-scope verdict at the `.lp` read, above) — re-owed with the catalogue on any deliberate move of that revision, and so re-owed at the move to `653ca5b` (the nesting limit and the raise's totality hold, the raise's depth handling O(depth)) and again at the move to `4f02758`: the occurrence-preserving raise leaves the nesting limit and the raise's totality intact and reads no filesystem, and the tiers `4f02758` adds — the construction-macros crate and the syntax-fusion doors — are not on keryx's `raise_source` path. - **The schema source, in the typical deployment** — operator configuration, not adversary input. keryx defends the schema doors regardless; the trust is the deployment's to grant, recorded not relied upon.

## The dependency boundary

Foreign code sits on more than one path, and only some carry foreign input. Containment sits at every foreign-code-meets-foreign-input crossing, and only there — by argument, not omission:

- **Descriptor-set door:** prost-reflect decodes bytes, and its accessors lazily decode as keryx's walk reads them; prost-types pre-reads for the shapes the engine cannot represent. Foreign input — *pre-empted for every shape known to panic or abort the engine* (editions, non-identifier names, an `uninterpreted_option` whose aggregate value the engine parses with an unbounded recursion) *and contained at both the decode and the walk* — the walk containment now stands as defense-in-depth behind those pre-emptions, its previously-known trigger (a deep resolved option via a lazy `options()` decode) foreclosed by the `uninterpreted_option` refusal.
- **Source door:** protox compiles source (and reads the filesystem). Foreign input — *contained here* (an unforeseen protox panic), *and pre-empted*: over-deep source (brace *and* option-aggregate nesting) and an over-large import graph are refused before protox's parser or its recursive import resolution overflows, and imports are confined to their include roots.
- **Payload door (binary, textproto, JSON):** prost-reflect decodes the payload — `DynamicMessage::decode` against the root type's descriptor for the binary wire format, `DynamicMessage::parse_text_format` for the text format, and `DynamicMessage::deserialize` driven by a serde_json deserializer for the JSON mapping — the one engine crossing per format on the payload path; the walk then reads the decoded tree through the engine's borrowing accessors, which decode nothing further, and keryx's own §6 scalar policy lowers every value. Foreign input — *contained at the decode* (`codec::engine`), in each format, recorded as **defense-in-depth with no known trigger**: no payload is known to fault the engine's binary decode, its text parse, or its JSON deserialization, whose failures are values (`UndecodablePayload`), so the frame stands behind a total door rather than in front of a known panic. The one *abort* the text parser is known for — a stack overflow on over-deep nesting, which no frame holds — is *pre-empted* ahead of it by the pre-parse guard and the sized parse thread (property 3); the JSON form's one abort axis — the same overflow beneath a deserializer that bounds its count but not the stack its count spends — is pre-empted by the sized decode thread alone, the count bounding what the thread must carry. For the text and JSON forms the frame sits inside the sized thread, on the thread the parse or deserialization runs on — the thread a panic hook consults `is_containing` from; a panic escaping it (none can, the frame catching every unwind inside it) is re-raised inside a frame on the caller's thread, so it is the same `DependencyFault` from the one seam, reported once. The JSON form's frame names **serde_json** — the code keryx calls — and the engine's `serde` visitors run beneath the deserializer inside that one frame, so a fault in either reads as that dependency's.
- **Outbound door (Increment 4), the `.lp` read:** themelios's single `raise_source` door — parse then raise behind it — turns `.lp` text into the answer set's symbols — the CLI's `keryx emit` reading a fixture or a solver's written output; the library seam takes symbols and crosses nothing here. Foreign input — *contained at the crossing* (`Dependency::Themelios`, the variant that door adds; one `fault::contain` frame around the `raise_source` call), recorded as **defense-in-depth with no known trigger**: the parser bounds its own nesting (`NestingLimit::DEFAULT`; past it `nesting-too-deep`, a diagnostic) and is total and iterative, the raise is total (never a panic; O(depth); its diagnostics values), so nothing of keryx's pre-empts ahead of them (property 3, branch (a)); text that does not raise to facts — a parse diagnostic, a statement that is not a fact — is `UnreadableAnswerSet`, a value. The `.lp` **admission** door (`keryx check`, Increment 6) crosses the same code and extends this frame as it lands.
- **Outbound door (Increment 4), the encode:** prost-reflect builds the message keryx's reassembly walk assembles (`DynamicMessage::new`, `try_set_field`) and serializes it — `encode_to_vec` for the binary wire format, `to_text_format` for the text format, its `Serialize` impl driven by serde_json for the JSON mapping — the one engine crossing per format on the outbound path, the payload door's decode mirrored. Foreign input — *pre-empted for the one panic axis known*: an encoder's mismatch panic, foreclosed by construction, every field set through the validating setter after keryx's inverse §6 lowering (*What is assumed trusted*); *pre-empted for the one abort axis known*: the serializers' unbounded native recursion on nesting — the walk refuses past the uniform ceiling before any message is built, and the encode runs on a thread keryx sizes (`engine::ENCODE_STACK`) with the frame *inside* it, as the text parse and the JSON decode run; *and contained at the encode* (`Dependency::ProstReflect`, its doc widened to name this crossing; for the JSON form the frame names **serde_json** — the code keryx calls — with the engine's `Serialize` visitors running beneath it inside the one frame, as inbound), recorded as **defense-in-depth over an axis already foreclosed**. The frame sits inside the sized thread, on the thread the encode runs on; an unwind escaping it (none can, the frame catching every unwind inside it) is re-raised inside a frame on the caller's thread — the one `DependencyFault` seam, reported once.
- **Emission:** themelios `construct`/`render` runs over keryx-**constructed** values, never foreign input — the generated modules (`core.lp`, `views.lp`, `emit.lp`) and the `.lp` fact module rendered from the symbols keryx built — interior code, trusted by the interior's own trust, needing no containment.

**The containment, and its honest ground.** At each such crossing keryx wraps the foreign call in one named `catch_unwind`, so an unforeseen unwinding fault becomes a typed `Diagnostic` rather than unwinding into the caller. Its ground is **architecture §6's totality posture — "no panics on foreign input"** — not a claim that a `Result` type forbids panics (it does not). On that ground the boundary is a **security mechanism with a named residual**, whose *motivation* is contract-honesty and the keryx user's experience; calling it "not a security guarantee" would be too modest for a reviewer deciding whether to count on it.

**The fault's diagnosis.** The contained fault surfaces as a new `DiagnosticKind`, **`DependencyFault`** (the enum is `#[non_exhaustive]`; a clean add). The case-split it serves is **asymmetric**: a *keryx* bug is a panic — keryx-core stays total by construction and mints no library "internal" kind — reported by the CLI as `Exit::Internal` ("a bug in keryx"); an *upstream* fault is `DependencyFault`, a value. It carries its own CLI exit class (a new `Exit` variant — an engine fault is neither a keryx bug nor a user's schema error). The dependency and operation keryx knows with certainty ride in the `detail` prose; the wire shape (`{field_path, kind, detail}`, specification Appendix B) is **unchanged** — the `kind` distinguishes the fault, and structured fields are not yet earned.

**The untrusted text this composes** is not unique to this boundary. Every diagnostic `detail` and `Locus` composed from input or foreign code is untrusted text — `unreadable_set` carries prost-reflect's message, `source_error` carries protox's (which quotes source), `MalformedOption` embeds a `Debug` of an adversary value, every `Locus::at(…full_name())` embeds an adversary-chosen name. So the property (composed text is escaped for the format it renders in, and length-bounded where an unbounded render would harm) belongs at the **diagnostics level**, held by the two renderers, and it differs by view: the **human view** (a terminal line) is both control-escaped and **length-bounded** — a fixed character cap on char boundaries, so an adversary's control bytes cannot steer a terminal and excess length cannot flood it; the **wire view** (machine-consumed JSON) is escaped for its format (`escape`, covering the C0 set) but bounded only by the input's own size, up to the constant escaping factor (a control byte becomes the six characters `\u00NN`) — never super-linearly — so a consumer reads the full `detail`. The one text outside a `Diagnostic` — the panic hook's opt-in `RUST_BACKTRACE` line, which prints a contained fault's payload (adversary-chosen names among it) — routes that payload through the same human bound, never raw. *Instrument (this pass):* a test that a `detail` or `Locus` carrying control bytes and excess length renders escaped and length-bounded in the human view, as `escape`'s test assures the C0 escaping for the wire.

**The panic-hook consequence, reconciled.** A panic hook runs at the panic site, *before* any `catch_unwind` unwinds. The CLI installs one (`exit::contain`) whose notice reads "this is a bug in keryx." A `DependencyFault` contained at a door would trip that hook — the user seeing "a bug in keryx" (false — the fault is upstream's, provoked by the input) *and* the `DependencyFault` diagnostic (under `--format json`, two arrays for one event). The reconciliation chosen (over swapping the global hook — process-global mutation that races other threads' panics — or neutralizing the notice — which loses the keryx-bug signal): the hook **consults `keryx_core::is_containing()`**, a thread-local set for the duration of a `fault::contain` frame, and stays silent while containing, so a contained fault reports once, as its diagnostic. Its **named residual costs**: (i) a library consumer with Rust's *default* hook still sees `panicked at …` for a contained fault, and silences it only by installing a hook that consults `is_containing`; (ii) the silence is default-only — under `RUST_BACKTRACE` the hook still emits the fault's location and backtrace, framed as a *dependency* fault (a debugging aid the operator opts into), since the returned diagnostic carries the payload message but not the location; (iii) a *non-unwinding* panic inside a frame (e.g. a `Drop` panicking during unwind) fires the hook while containing and then aborts with only the runtime's line — an accepted residual inside *The residual*'s abort case, with no stable-Rust guard (`PanicHookInfo::can_unwind` is unstable). It retired three standing statements of the old posture, updated as it landed: architecture §6, the `descriptor::decode` note, and `docs/proto-support.md`.

**The residual.** `catch_unwind` holds only an *unwinding* panic; under `panic = abort`, and for a fault that aborts, hangs, or corrupts rather than unwinds, there is nothing to catch — so the known *abort* axes are **pre-empted, not contained**: the descriptor door refuses an `uninterpreted_option` (whose aggregate the engine parses unboundedly), the source door bounds bracket depth and the import graph, the payload door's text form bounds its message nesting before that same unbounded parser and sizes the thread the parse runs on, and its JSON form sizes the thread its deserialization runs on for the deserializer's own full admit, and — committed for the outbound door — the reassembly walk refuses past the ceiling before the engine's unbounded serializers recurse and the encode runs on a thread keryx sizes, each before the overflow. What the residual still covers — an *unforeseen* abort, `panic = abort`, a hang — is closed by *The division of labor*.

**Process-global state.** A contained fault must not poison state shared across requests. prost-reflect touches its global well-known-type pool only through `DescriptorPool::global()`, which holds the pool's lock solely across an infallible `Arc` clone (verified against the pinned source, `global.rs`), never across the panic-prone decode; its only across-fallible-work holders are the `*_global_*` mutators, which keryx never calls. So a contained fault leaves the pool usable — a clean decode in the same process still succeeds (instrumented) — and one fault cannot become a persistent denial for a long-lived service, which settles the `catch_unwind`-soundness question for the shipped doors. The payload door reads the pool only through the root descriptor's handle, in each of its three formats — the engine consults its global well-known-type pool on a descriptor's option decode and in its reflection of prost-types' own well-known types (its every `global()` site, cited at `codec::engine`), never on a payload decode, parse, or deserialization; the text parser resolves an `Any` value's type against the root descriptor's own pool, and the JSON deserialization resolves one against that same pool (`desc.parent_pool()`, cited at `codec::engine`), never the engine's global one — so no payload path touches process-global state at all. The outbound door owes the same argument for its two crossings as they land — that the encode reads the pool only through the root descriptor's handle, and that themelios's parse and raise hold no process-global state — each cited at its site, so a contained fault there leaves the process as usable as one at the payload door does; committed, *Increment 4*. *Residual:* a same-process consumer that itself calls those global mutators with a panicking set is outside keryx's control, named here.

## The division of labor

keryx is the translation; a consuming service runs the solver and owns deployment (R4). Fault-containment divides on that line.

- **keryx guarantees:** totality (by construction, plus the contained boundary under unwinding), bounded allocation and bounded-depth walks, integrity, determinism, and the full insulation of its dependencies from its user.
- **The consuming service provides** what only a process boundary can: isolation of the translation under resource limits, so that an unforeseen fault keryx's in-process containment cannot catch — an abort, a hang, a corruption — is contained by the operating system. A mission-critical embedding runs keryx's translation isolated; keryx names the requirement and does not over-claim a total in-process guarantee. The service also owns the trust placement (a trusted schema source) and the build profile (unwinding, to keep the contained boundary live).

## The doors

Each door: its input, its trust in the typical deployment, the foreign code it invokes, its walks, its per-property **status** (*held at `b093008`* / *this pass* / *held for binary* / *held for binary and textproto* / *held for binary, textproto, and JSON* / *Increment N*), its instruments, and any operator recommendation.

### Descriptor-set door — `descriptor::ingest(&[u8])` — shipped

- **Input.** A serialized `FileDescriptorSet`. **Trust.** Schema (operator, typically). **Foreign code.** prost-reflect (`DescriptorPool::decode`, and the lazily-decoding accessors the walk reads); prost-types (the pre-read). **Walks.** `subject_messages` (gathers nested message types, a managed stack); `recursion::reaches_self` (the containment-cycle walk); the per-element `build_*` pass; the referent closure (a heap worklist that pulls in every well-known or dependency type a subject field references, §10 — each type built once, bounded by the pool's finite type set, no call-stack recursion).
- **Status.**
  - *Totality:* the structural refusals `MalformedDescriptor`/`MalformedOption` hold — *held at `b093008`*; *this pass* pre-empts every shape the engine panics or **aborts** on rather than rejects — editions, an unrecognised `syntax`, a **package or declared name that is not a proto identifier** (the leading-dot name the engine panics on among them), and any **`uninterpreted_option`** (a compiled set carries none; an unresolved one drives the engine's unbounded text-format parse of its aggregate value, an abort containment cannot hold) — and **contains an unforeseen engine fault at both the decode and the accessor walk** (the accessors lazily decode, keryx's walk holds no `unwrap`/`expect` of its own, so a walk fault is the engine's `DependencyFault`, not a keryx bug). The walk containment now stands as **defense-in-depth** behind the pre-emptions — its previously-known trigger (a deep resolved option through `options()`' lazy decode) foreclosed by the `uninterpreted_option` refusal — with a *real* contained fault demonstrated at the decode. Both totality generators are *this pass*.
  - *Bounded depth:* `recursion::reaches_self` is an explicit managed stack already — *held at `b093008`*; `subject_messages` is a managed stack *this pass* (native recursion before it).
  - *Bounded work:* the Θ(*n*·*d*) profile is the truth today; the allocation-budget instrument is *this pass*.
  - *Integrity, determinism:* *held at `b093008`* (the refusal set; the golden tests).
- **A boundary this door crosses.** The `package` string is adversary-controlled here yet reaches two sinks that each assume an identifier shape — the CLI's per-package output path (`<out>/<package>.…`, a filesystem *write*) and the emitted `#include "<package>.core.lp"` operand (a clingo directive) — so an unvalidated package could name a traversing path or inject a directive through the `.lp` a consumer loads. *This pass* refuses at the door any package that is not a dotted sequence of proto identifiers within a segment bound, and *represents* the proof: a `Package` newtype constructed only at the door and carried to `Unit::package()`, so neither sink re-derives trust from a bare string. Integrity (property 4) is thereby held for the package too — it reaches the path and the `#include` only as a validated identifier.
- **A named vector at this door.** Option admission is a **file-name heuristic** (`descriptor::options::read`: an extension is keryx's iff its declaring file is *named* `keryx/options.proto`), not true extension identity — a crafted set can self-declare that file name (`options.rs` documents this). *Totality* survives it: a non-identifier option key is diagnosed downstream (`UnmappableOptionKey`), not panicked. *Integrity* survives it **today**: no annotation semantics are consumed at the gen stage, so a spoofed registry changes only `opt/3` facts, which faithfully report what the set declared; the obligation re-arises when an annotation gains meaning (Increment 5). Replacing the file-name heuristic with true extension identity is an additive follow-up.
- **Instruments.** The two totality generators; the deep-nesting test (attaching per the depth property); the allocation-budget test; a same-process clean-decode-after-fault test (the global-pool argument).

### `.proto`-source door — `descriptor::source::compile(files, includes)` — shipped

- **Input.** `.proto` file paths and include roots. **Trust.** Schema; **not** recommended at an untrusted per-request boundary. **Foreign code.** protox (compiler and resolver chain), which **reads the filesystem**. **Walks.** the descriptor door's, downstream of the compiled set.
- **Status.** Totality, integrity, and determinism ride the descriptor door's walk over the compiled set — *held at `b093008`*. *This pass:* an unforeseen protox panic is contained (`DependencyFault`); **over-deep source and an over-large import graph are pre-empted** — keryx's guard refuses source whose **bracket depth** exceeds `SOURCE_NESTING_LIMIT` (`SourceTooDeep`), counting `{ }` message/group nesting *and* `< >` option-aggregate nesting (the aggregate value prost-reflect re-parses unboundedly at option resolution), and refuses an import graph exceeding a file-count budget (`SourceImportGraphTooLarge`), each *before* protox's unbounded parser or its recursive import resolution overflows the stack and aborts (pre-emption instances beside the descriptor pre-read, property 1). The scanner's state machine mirrors protox-parse 0.9.0's lexer, the pinned lines cited at `source.rs`. The walk over the compiled set is bounded (the managed stack) and its work bounded, as for the descriptor door; **confinement** is *held for escapes* (below). Bounded depth takes property 3's branch **(b)** on two axes (the bracket scan, structural; the import budget, a chosen number), each defense-in-depth with a **residual**: a sub-standard thread stack can abort below the bound — measured (debug) at ~900 nesting levels and ~1800 chained imports on an 8 MB main stack, and release frames are smaller (so its threshold is higher); the bounds (99 and 128) sit below the ~0.8 MB floor that scales to, closed by the consuming service's process isolation (*The division of labor*).
- **Resource selection / confinement.** This door **selects files by design**: an `import` in adversary-supplied source names a file the resolver reads and folds into the set — so its defended property is **confinement**: the resolver reads only within the include roots, not a traversing (`..`), absolute, or symlinked import out of them. **Status: held for escapes.** protox's own import-name validation rejects a `..`/absolute import *name* (`UncompilableSource`); keryx's include-root resolver canonicalises the resolved path and refuses one that escapes its root (`SourceOutsideRoot`), catching the **symlinked** escape protox does not and backstopping the rest. **WKT/registry *shadowing*** — a user file named like a well-known type or the option registry placed *inside* a root, which resolves first by chain precedence — is **not** an escape and is **not** closed by this mechanism (mechanising it would fight the deliberate "a project's own `keryx/options.proto` wins" order, `source.rs`); it is **answered** — a shadow substitutes *in-root* content for a bundled constant, so nothing outside the root is read: the confidentiality half leaves no path, and the integrity half (a shadow that redefines an option message) is the descriptor door's registry-shadowing vector, held today. **Confidentiality** (property 6): source-import exfiltration is thereby **closed**. Two low residuals sit outside the model's adversary (who supplies the root's contents at call time, not a concurrent mutator): a writer who swaps a directory component for a symlink between canonicalise and read, and a hard link inside the root to a file outside it — both need write access inside the root during the call, named not relied upon.
- **Recommendation.** At an untrusted boundary, accept a **pre-compiled descriptor set** from a trusted source; treat `.proto`-source compilation as an operator or CLI convenience. keryx-core keeps the door total and bounded regardless; the recommendation steers where the compiler-on-hostile-input surface is exposed.
- **Instruments.** The confinement tests above — *this pass* — hold the escapes (`tests/source_confinement.rs`: the symlinked escape is refused, the in-root read admitted); where a property rests on a claim about protox's behavior the repository cannot itself check, the door's status names it as such (the pinned-source citations in `source.rs`).

### Payload door — `codec::Codec::shred(root_type, payload, format, root)` — shipped for binary, textproto, and JSON

- **Input.** A message payload: the binary wire format (`PayloadFormat::Binary`; the CLI's `.binpb`), the protobuf text format (`PayloadFormat::Textproto`; the CLI's `.txtpb`), and the protobuf JSON mapping, canonical (`PayloadFormat::Json`; the CLI's `.json`) — all three as of the inbound codec, through the same `Codec`, the same walk, and the same admission policy. **Trust.** Payload — per request, the adversary's: the hot door, and the reason the model precedes the increment. **Foreign code.** prost-reflect (`DynamicMessage::decode` against the root type's descriptor for the binary format; `DynamicMessage::parse_text_format` for the text format, on a thread keryx sizes; `DynamicMessage::deserialize` for the JSON mapping, driven by a serde_json deserializer, on a thread keryx sizes; then the borrowing field accessors the walk reads, which decode nothing further) and serde_json (the JSON deserializer, whose own recursion limit is the JSON form's outer depth bound). **Walks.** the shredding walk (`codec::walk`) — an explicit heap stack of work items, one per message occupant, under the uniform nesting ceiling — over a referent index built once per codec (predicate-keyed sort and enum resolution, so the walk never searches); and, for the text format, the pre-parse depth guard's scan (`codec::guard`) ahead of the parser — one pass over the payload's bytes, allocation-free, no recursion. The JSON form adds no scan: its deserializer bounds its own nesting, and keryx reads nothing of the payload ahead of it.

### Outbound door — `codec::Codec::reassemble(answer_set, format)` and the CLI's `.lp` read (`keryx emit`) — built for the binary, textproto, and JSON forms

- **Input.** An answer set: a `Vec<Symbol>` over the generated vocabulary — the consuming tool's solver's output on the library seam, or `.lp` text the CLI reads (`keryx emit`; a fixture, or a solver's written model) and raises to symbols through themelios — reassembled into one message per `emit_t` root, in the binary wire format, the text format, or the JSON mapping (`PayloadFormat`, the three the payload door admits; the CLI's `--out binpb|txtpb|json`). One door, two foreign crossings — as the payload door is one door over a decode and a walk: the **`.lp` read** (themelios `parse`/`raise`, on the text path only) and the **encode** (prost-reflect's construction and serialization, on every path). **Trust.** The answer set is the adversary's, as the payload's text is inbound: the solver's output over a model keryx does not control and facts the payload sender shaped, per request — the response half of the hot path — and a fixture is foreign text by the same rule; *regardless of embedding*, the door is defended to the bar. **Foreign code.** themelios (`parse`, then `raise`, on the `.lp` path); prost-reflect (`DynamicMessage::new` and `try_set_field` as the walk builds; `encode_to_vec`, `to_text_format`, and its `Serialize` impl as it serializes, on a thread keryx sizes); serde_json (the JSON serializer the `Serialize` impl is driven through). **Walks.** the reassembly walk (`codec::assemble`) — an explicit heap stack of work items, one per occupant, top-down from each `emit_t` root, under the uniform ceiling — over a **slot index** built once per call: a `BTreeMap` keyed by field predicate and parent occupant, filing a field atom `f(O, …)` by its predicate and first argument and an occupancy atom `u(t)` by deconstructing its occupant `t = f(P, …)`, so one query yields a scalar field's atoms and a message field's children alike, the walk joins on occupancy, and it never searches (no hash table). No walk of keryx's precedes the `.lp` read: themelios bounds its own.
- **Status.** **Held for the binary, textproto, and JSON forms.** The reassembler over the answer set, the encode in all three output forms, and the CLI's `.lp` read are built to the commitments below and instrumented. `reassemble` takes a `format` argument (`PayloadFormat`) and emits the binary wire form, the protobuf text format, or the canonical JSON mapping; the CLI reads an `.lp` answer set through themelios (`codec::answer`) and `keryx emit` writes one message to stdout in the form `--out` names.

  - *Confidentiality:* out of scope — no filesystem or network reach (property 6); the CLI's read of the `.lp` path it is given is adapter plumbing (*Not doors*).
- **The untrusted text this door composes.** A `TermTypeMismatch` names the term's *kind* — a string where an integer is declared — never its text, the answer set being the adversary's to flood a diagnostic with, as the payload's text is inbound; a `ShapeViolation` names the field path and the obligation broken; a `Locus` is a field's fully-qualified proto path, schema text admitted at the descriptor door; `ReassembledTooDeep` names the depth and the ceiling and nothing of the answer set; `UnreadableAnswerSet` composes themelios's own diagnostic message — which may quote the text — held to the diagnostics-level rendering bound like every other, and to no weaker one.
- **Instruments.** Built (`crates/keryx-core/tests/`): `codec_reassemble.rs` (the door's shape — one message per marker, the root carried, results marker-ordered, every-diagnosis-or-none), `codec_roundtrip.rs` (payload → facts → payload on the thermal `ReadingBatch` and `Reading`, canonical zero-omission, and three-way round-trip parity across binary, textproto, and JSON over the batch and the map/enum shapes), `codec_emit_depth.rs` (the ceiling refused before any build; a ceiling-deep message encoding on the sized thread from a 512 KiB caller; the large-index refusal without an allocation), `codec_emit_determinism.rs` (same and shuffled answer sets → identical bytes, per output form, a map key-ordered whatever order its entries arrive in), `codec_emit_totality.rs` (two generators: the arbitrary generator, 512 cases over mixed vocabulary in every form → no panic, every diagnosis a reassembler kind; and the vocabulary-aware fixed-seed reach-tally sweep, reassembling and round-tripping valid trees of growing breadth in every form), `codec_emit_shapes.rs` (the map, enum, singular-message, and repeated-scalar forms round-tripped through the door, with the undeclared-enum and duplicate-map-key refusals), `codec_answer_totality.rs` (the `.lp` read's totality over arbitrary and clingo-shaped text — symbols or `UnreadableAnswerSet`, never a panic), `codec_emit_wkt.rs` (the JSON encode's well-known-type refusal — an out-of-range `Timestamp`/`Duration`, an unresolvable `Any` — refused in JSON with `UnrepresentableJson`, carried structurally in binary and textproto), and the encode adapter's per-site boundary test in `codec::engine` (`the_setter_forecloses_a_mismatch_at_every_encode_site`); and (`crates/keryx-cli/tests/`) `emit.rs` — the CLI's `emit`: one message on stdout in each `--out` form; `Usage` on two roots; `Exit::Shape` on a shape, term-type, or unreadable-answer-set refusal; `Input` on a missing `.lp`.

## Open — named here, settled elsewhere

Still open, by measurement or by a later increment:

- **Cost acceptability** — whether the Θ(*n*·*d*) allocation and the quadratic cycle analysis (`recursion::mark`) are acceptable against a deployment's limits (measurement). Name qualification is no longer among these — it is bounded (property 2).
- **Proto2 `required` completeness, outbound (Increment 4)** — `emit.lp` emits totality for implicit-presence fields only, the `Mapping`'s totality not yet distinguishing a proto2 `required` field from an explicit-presence one; so a `required` field's completeness is unchecked at Increment 4, at solve time and at reassembly alike — a message omitting one is produced, faithful to the answer set that omitted it (an under-representation, never a misrepresentation; property 4). Committed future, not a boundary: the `Mapping` widened so the obligation is emitted and enforced — full proto2 and proto3 outbound parity — in a later increment.
- **Increment-5 obligations carried** — option-admission *integrity* re-arises when an annotation gains meaning (held today because none is consumed); the overlay, manifest-read, and protoc-plugin doors are built to this model as they land.

**Answered or settled** — at the hardening pass and, where marked, at the inbound codec or by the outbound door, now built (recorded at the doors above; ledgered here so the list is complete):

- **The codec's round-trip half** — *closed* (integrity, Increment 4): payload → facts → payload holds byte-for-byte on the thermal story, and the reassembled message shreds back to the same facts, in all three output forms; the reverse (answer set → payload → facts) holds over the map, enum, singular-message, and repeated-scalar forms too (`tests/codec_roundtrip.rs`, `tests/codec_emit_shapes.rs`).
- **The per-site encode foreclosure** — *closed* (totality, Increment 4): the setter's `is_valid_for_field` check forecloses a mismatch at each encode site's shape, verified against the pin and driven at every shape (scalar, list element, map key, map value, nested message, enum, packed) by `the_setter_forecloses_a_mismatch_at_every_encode_site`; format-independent, so the textproto and JSON encoders inherit it.
- **Source-import exfiltration / WKT-registry shadowing** — *closed* (confidentiality): a shadow substitutes in-root content only, so no import reads outside its root; the integrity half is the descriptor door's registry-shadowing vector, held today.
- **The descriptor door's `package` boundary** — *closed*: the package reaches an output path and the `#include` operand only as a door-validated, represented `Package` (a dotted identifier).
- **The text-format abort axis** — *pre-empted*: the descriptor door refuses `uninterpreted_option`, the source door counts `< >` nesting, before the engine's unbounded aggregate parse overflows; and the payload door's text form counts `{ }`/`< >` message nesting before that same parser sees a payload, then parses on a thread sized for what it admits (settled at the inbound codec).
- **The import-graph abort axis** — *pre-empted*: a file-count budget refuses an over-large import graph before protox's recursive import resolution overflows.
- **`catch_unwind` soundness** — *settled with a named residual*: prost-reflect holds the global pool's lock only across an infallible clone (cited), and keryx never calls its global mutators, so a contained fault does not poison shared state (a same-process mutator with a panicking set is the residual); `panic = abort` remains *The division of labor*'s.
- **Decode / recursion limits** — *settled for the shipped doors*: prost's `RECURSION_LIMIT` is 100 (deepest admitted lexical chain 99); the descriptor door takes branch (a), the source door branch (b) on the bracket axis plus the chosen import budget, and the payload door branch (b) by the uniform ceiling (99) — at the walk for binary, the engine's limit one level outside it; at the pre-parse guard for textproto, ahead of a parser that has no limit of its own — and branch (a) for JSON: serde_json's default recursion limit (128 containers, the 128th refused) is the outer bound, the walk's ceiling beneath it binding for a chain of singular message fields and the count binding first for repeated and map-of-message chains; and the outbound door, committed, the same ceiling at its reassembly walk.
- **Qualification complexity** — *fixed*: bounded rounds (property 2).
- **Hash-seed steering** — *not present*: keryx's own source holds no `HashMap`/`HashSet` (the only hash tables are foreign, std-seeded), so no input-reachable seed steers an output; the payload door sorts a map's entries by key before it walks them, so the engine's own table order never reaches the facts.
- **The payload door's compositional-depth branch** — *settled at the inbound codec (binary)*: property 3's branch (b), by the walk's uniform admission ceiling (99 message-typed levels below the root, derived from the engine's constant, one below it), binding at a binary payload's 100th level, with the engine's own decode limit the outer bound from the 101st on; spec §8 reconciled — a door-admission policy, not a limit of the translation.
- **The payload door's text-format depth and stack** — *settled at the inbound codec (textproto)*: property 3's branch (b) ahead of the engine — the pre-parse guard refuses nesting past the same ceiling before the engine's unbounded text parser sees a token, its dominance invariant exact over the parser for every payload it accepts, and over the walk exact for singular and repeated message fields while conservative for map entries and expanded `Any` — those two forms bind at a shallower message depth in text than on the wire (about 49 map-of-message levels against 99), never a deeper one, a settled and documented limitation; and the residual a sub-standard caller thread would be is closed by construction, the parse running on a thread keryx sizes for the deepest admitted payload (8 MiB, some three times the measured debug need at 99 levels), where the source door's guard leaves its residual to process isolation.
- **The payload door's JSON depth and stack** — *settled at the inbound codec (JSON)*: property 3's branch (a) at the engine — serde_json's own recursion limit, on at its exact pin and never lifted, is the outer bound (127 nested containers admitted, the 128th refused), with no guard of keryx's ahead of it; the walk's uniform ceiling binds beneath it for a chain of singular message fields (99 admitted; 100 through 126 the walk's refusal; 127 the deserializer's), the one door where the walk's counter is the binding refusal for more than a single level; a repeated or map-of-message chain meets the deserializer's count first, at about 63 levels (two containers a level), and a `google.protobuf.Value` chain the engine's own message-decode limit at about 50 — shallower than the ceiling, never past it, the singular and repeated boundaries instrumented and the map and `Value` bindings documented from the engine's measure of record, not instrumented, for want of a fixture; the deserialization runs on a thread keryx sizes for the deserializer's full admit (8 MiB, some four times the measured debug need of the costliest form), the containment frame inside it naming serde_json; and the one cross-form asymmetry — an empty payload is no JSON value where the wire and text read the empty message — is a refusal, never a misreading.
- **The outbound door's depth branches** — *settled by design and built (Increment 4)*: the `.lp` read takes branch (a) at themelios — its parser bounds its own nesting and its raise is total, so no guard of keryx's precedes them — and the encode takes branch (b) by the reused ceiling (`walk::NESTING_CEILING`, the inbound constant itself) at the reassembly walk, ahead of serializers that bound nothing of their own, with the encode on a keryx-sized thread (`engine::ENCODE_STACK`, its 8 MiB now measured to hold a ceiling-deep encode with wide margin — some 640 KiB in debug, 192 KiB in release for the costliest of the three encoders) and the containment frame inside it; spec §8's discharge is the payload door's, a door-admission policy.
- **The encode's mismatch-panic axis** — *foreclosed by construction (the setter is format-independent, so the binary, textproto, and JSON encoders share it)*: every field set through the engine's validating setter after keryx's inverse §6 lowering, the setter's deep `is_valid_for_field` check the complement of the switch the encoders panic outside, verified per panic site against the pin and driven at each site's shape by `the_setter_forecloses_a_mismatch_at_every_encode_site`; the containment frame defense-in-depth over it.
